# Redis 基础
### Redis 介绍
Redis 是一款‌开源的内存键值数据库‌，全称为 Remote Dictionary Server，支持字符串、哈希、列表、集合等多种丰富数据类型，具备高性能、持久化、高可用特性，是互联网系统中最常用的缓存中间件，现在已逐步演进为支持AI场景的实时数据平台。

### Redis 适合解决什么问题
热点数据缓存：降低数据库压力，提升接口响应速度。
分布式锁：解决分布式系统中多实例的资源竞争问题。
实时计数器：实现点赞、浏览量等高频计数场景。
消息队列：基于Stream数据结构实现轻量可靠的消息队列。
排行榜/限流：利用有序集合实现排行榜，基于令牌桶/漏斗算法实现接口限流。
向量检索：适配AI场景下的向量相似度搜索需求。

### ‌Redis为什么快
完全基于内存操作，数据读写都在内存中，避免了磁盘IO的开销。
使用I/O多路复用技术，单线程高效处理大量并发客户端连接。
数据结构设计极致优化，不同场景匹配专属高效数据结构。
避免了多线程上下文切换和锁竞争的额外性能损耗。

### Redis为什么单线程还能这么快‌
这里的“单线程”指的是‌核心执行命令的主线程是单线程‌，并非整个Redis只有一个线程：
纯内存操作：内存读写速度是纳秒级，远快于磁盘IO，单线程完全可以处理。
I/O多路复用：通过epoll等机制，单线程可以同时监听上万客户端连接，不会被IO阻塞。
无多线程开销：避免了多线程频繁上下文切换、锁竞争、死锁等额外开销，CPU利用率极高。
高效的数据结构：底层对SDS、跳表等结构做了大量优化，命令执行效率极高。

### Redis主要用途
1. 高性能缓存‌
把高频访问的热点数据存入内存，大幅降低数据库查询压力，将接口响应速度从百毫秒级压缩到微秒级，是系统性能优化的首选方案。
2. Session 共享‌
在多服务器集群部署中，将用户登录态、购物车等会话数据统一存入 Redis，解决不同服务器间 Session 不同步的问题，实现跨节点的用户身份识别。
3. 排行榜‌
利用 Redis 有序集合（ZSet）的天然排序特性，轻松实现游戏积分榜、商品销量榜、热搜榜等场景，支持实时更新和快速分页查询。
4. ‌消息队列‌
借助 List 或 Stream 数据结构，实现轻量级消息队列，处理异步任务、流量削峰，无需额外部署 RabbitMQ 等中间件即可完成简单的消息生产消费。
5. ‌分布式锁‌
通过 SETNX 等原子命令实现跨服务的互斥访问，避免多个进程同时操作共享资源引发的数据冲突，是分布式系统中保证数据一致性的核心手段。
6. ‌限流‌
基于计数器或令牌桶算法，限制同一 IP/用户单位时间内的接口访问次数，防止恶意请求把系统打垮，保障服务稳定性。
7. ‌GEO 地理位置‌
利用 Redis 内置的地理位置索引，存储经纬度信息，快速实现“查找附近5公里内的商家”这类LBS场景，计算效率远高于传统数据库。
8. ‌Bitmap 位图‌
用二进制位记录用户签到、在线状态等布尔信息，占用空间极小，比如统计亿级用户的连续登录天数，仅需几MB内存即可完成。
9. HyperLogLog
专门用于大数据量下的基数统计，在误差可接受的范围内，用极小的内存完成亿级页面独立访客（UV）的去重统计，远优于传统的集合去重方案。

| HyperLogLog | HyperLogLog | 页面UV统计 | 极高 |

### 安装
```
docker

# 1. 拉取镜像
docker pull redis:7.2

# 2. 启动容器
# -d: 后台运行
# --name: 容器名称
# -p: 端口映射 (宿主机6379:容器6379)
# -v: 挂载配置文件和数据目录（持久化关键）
docker run -d \
  --name my-redis \
  -p 6379:6379 \
  -v /my/redis/conf/redis.conf:/usr/local/etc/redis/redis.conf \
  -v /my/redis/data:/data \
  redis:7.2 \
  redis-server /usr/local/etc/redis/redis.conf \
  --appendonly yes
```
Redis 核心配置 (redis.conf)
Redis 的配置主要通过 redis.conf 文件完成，生产环境需重点调优网络、内存、持久化和安全四大模块。

| --- | --- | --- |
| bind | 监听 IP | 默认 127.0.0.1。生产环境若需外网访问，改为内网 IP 或 0.0.0.0（务必配合防火墙）。 |
| port | 监听端口 | 默认 6379。多实例部署时需区分不同端口。 |

| protected-mode | 保护模式 | 默认 yes。若未设密码且 bind 为 0.0.0.0，仅允许本地访问。生产环境建议设密码并关闭此模式或严格限制 bind。 |

| --- | --- | --- |
| save | RDB 快照规则 | save 900 1（900秒内1次修改即保存）。适合定期备份，恢复速度快但可能丢失少量数据。 |

### Redis 命令
1. ‌ping‌
‌作用‌：测试客户端与 Redis 服务器的连接是否正常。
‌返回‌：若连接正常返回 PONG，否则报错或超时。
‌场景‌：健康检查、心跳检测。
2. select‌
‌作用‌：切换当前连接的数据库索引。
‌语法‌：SELECT index（默认范围 0-15，共 16 个库）。
‌注意‌：Redis Cluster 集群模式不支持多 DB，只能使用 db0。
3. keys
‌作用‌：查找所有符合给定模式的键。
‌语法‌：KEYS pattern。
‌注意‌：Redis Cluster 集群模式不支持多 DB，只能使用 db0。

为什么不要使用 keys *
严禁在生产环境使用 KEYS *，因为它会阻塞 Redis 单线程，导致服务瞬间不可用。
时间复杂度 O(N)：KEYS * 需要遍历 Redis 中‌所有‌键值对进行匹配。
阻塞单线程：Redis 处理命令是单线程的。执行 KEYS * 期间，Redis ‌无法响应其他任何请求‌（如读写操作）。
替代命令：SCAN 。使用 SCAN 命令代替 KEYS，它基于‌游标迭代‌，分批次返回结果，不会长时间阻塞主线程。

4. exists‌
‌作用‌：检查 key 是否存在。
‌返回‌：存在返回 1，不存在返回 0。
‌场景‌：缓存穿透判断、前置校验。
5. ‌expire‌
‌作用‌：为 key 设置过期时间（单位：秒）。
‌语法‌：EXPIRE key seconds。
‌场景‌：验证码、会话 Token、临时缓存。
6. ‌ttl‌
‌作用‌：查看 key 的剩余生存时间。
‌返回‌：
>0：剩余秒数
-1：永不过期
-2：key 不存在
7. persist‌
‌作用‌：移除 key 的过期时间，使其永久有效。
‌返回‌：成功移除返回 1，key 不存在或无过期时间返回 0。
8. ‌rename‌
‌作用‌：修改 key 的名称。
‌语法‌：RENAME old_key new_key。
‌注意‌：若 new_key 已存在，会被覆盖。原子操作。
9. ‌move‌
‌作用‌：将当前数据库的 key 移动到指定数据库。
‌语法‌：MOVE key db_index。
‌限制‌：仅在单机多 DB 模式下有效，Cluster 模式不支持跨库移动。
10. ‌del‌
‌作用‌：同步删除一个或多个 key。
‌机制‌：立即释放内存，阻塞主线程。
‌场景‌：删除小对象或少量 key。
11. unlink‌
‌作用‌：异步删除 key。
‌机制‌：先从字典中移除 key（瞬间完成），后台线程异步释放内存。
‌场景‌：删除大 Value（如大 Hash、List），避免阻塞主线程，Redis 4.0+ 引入。
12. ‌flushdb‌
‌作用‌：清空‌当前‌所选数据库的所有 key。
‌风险‌：不可逆，生产环境慎用。
13. ‌flushall‌
‌作用‌：清空‌所有‌数据库（0-15）的所有 key。
‌风险‌：极高危操作，通常用于重置测试环境。

| 类别 | 命令 | 关键特性/风险 |
| --- | --- | --- |
| ‌删除‌ | DEL | 同步阻塞，删大值慢 |
|  | UNLINK | 异步非阻塞，删大值推荐 |
| ‌查找‌ | KEYS | O(N) 全量扫描，‌生产禁用‌ |
|  | SCAN | 游标迭代，生产推荐替代 KEYS |
| ‌清理‌ | FLUSHDB | 清当前库 |
|  | FLUSHALL | 清所有库 |

### Redis Key设计
1. Key 命名规范
推荐采用‌业务模块:子模块:ID:属性‌的分层命名结构，统一用英文半角冒号:分隔层级，所有字符使用小写字母、数字、英文点号，禁止出现空格、下划线、引号等特殊字符，以英文字母开头，避免大小写混淆产生重复Key。

集群场景优化：使用Hash Tag将关联Key指定到同一槽位，避免数据倾斜，比如order:{10001}:items，保障同订单相关操作可在集群内正常执行。
额外要求：层级深度不超过5级，可在末尾追加value类型标识（如:string），进一步提升可读性。
2. Key 长度最佳实践
Redis单Key理论最大长度可达512MB，但实际业务中需严格控制：
推荐将Key长度控制在‌30-150字节‌区间，典型场景30-50字符即可平衡可读性与内存占用。
优化技巧：在语义清晰的前提下对常用单词做合理缩写，比如将user简化为u、message简化为msg，避免无意义的超长Key浪费内存空间。
3. Key 过期策略推荐
所有业务Key必须设置合理过期时间，禁止大量永久Key长期占用内存：
常规缓存场景：根据数据更新频率设置TTL，比如用户登录态设为3600秒（1小时）、商品基础信息设为86400秒（1天）。
热点数据场景：采用“访问续命”机制，当Key被命中时自动延长过期时间，既避免冷数据长期留存，又保障热数据不会被提前淘汰。
避坑要点：批量设置过期时间时需打散TTL，比如给1000个同批次Key的过期时间叠加随机偏移量，避免大量Key同时过期引发缓存雪崩。
4. Key 数量规划方法
Redis理论最大Key数量约为2^32（42.9亿），实际可承载量由内存决定：
容量估算：按单Key+Value平均占用100字节计算，1GB内存约可存储1000万个Key，提前根据业务内存配额规划总Key上限。
超量优化：当Key量级达到千万级以上时，可采用Key分片策略，通过CRC32/MD5哈希取模将Key分散到多个实例，也可将多个小Key聚合到同一个Hash结构中，大幅降低全局Key总数。
日常运维：通过dbsize命令定期监控Key总量，用非阻塞的SCAN命令遍历清理长期未访问的冷Key，避免Key无限制膨胀。

# Redis 数据类型
### string
1. 基础特性
Redis的String是‌二进制安全‌的数据结构，底层基于SDS（简单动态字符串）实现，单值最大支持512MB存储，是所有Redis数据类型中使用频率最高的类型，覆盖超50%的常规业务场景。
2. 字符串场景
核心操作：支持SET/GET基础读写，搭配MSET/MGET批量操作减少网络IO开销，还可通过APPEND追加内容、GETRANGE截取子串、STRLEN获取字符串长度。
典型用法：存储用户序列化信息、配置参数、页面缓存等，是最通用的KV存储实现方式。
3. 数字场景
核心操作：提供原子性的数字操作命令，包括INCR（自增1）、DECR（自减1）、INCRBY（指定步长自增）、DECRBY（指定步长自减）、INCRBYFLOAT（浮点数自增）。
典型用法：实现网站访问量、文章点赞数、分布式限流计数器等场景，单命令原子性可避免高并发下的计数冲突问题。
4. 二进制场景
核心特性：完全基于二进制存储，不会做任何编码转换，存入的内容和取出的内容完全一致，天然支持图片、音频、序列化对象等任意二进制数据。
注意事项：单值大小建议控制在100KB以内，过大的二进制内容会拖慢Redis单线程的处理效率，引发阻塞风险。
5. 命令
SET‌：设置指定 key 的值。如果 key 已经存在，则覆盖旧值。
SET key value [EX seconds] [PX milliseconds] [NX|XX] [KEEPTTL]

GET:获取指定 key 的值。
‌语法‌：GET key
‌返回值‌：如果 key 存在，返回对应的字符串值；如果 key 不存在，返回 (nil)。在很多编程语言的客户端中，它会被解析为 null、None 或 nil

APPEND‌：为指定的 key 追加值。
APPEND key value

STRLEN‌：返回 key 所储存的字符串值的长度。
‌语法‌：STRLEN key

‌INCR/‌DECR：将 key 中储存的数字值增/减一。
语法‌：INCR/DECR key

MSET‌/MGET：同时设置/获取多个 key 的值。
语法：MSET key value [key value ...] MGET key [key ...]

‌SETNX‌ (Set if Not eXists)：只有在 key ‌不存在‌时，才设置 key 的值。
‌语法‌：SETNX key value

GETSET‌
‌功能‌：将给定 key 的值设为 value，并返回 key 的‌旧值‌。
‌语法‌：GETSET key value

| 命令 | 时间复杂度 | 核心用途 | 注意事项 |
| --- | --- | --- | --- |
| ‌SET‌ | O(1) | 设置值 | 默认覆盖旧值并清除过期时间 |
| ‌GET‌ | O(1) | 获取值 | key 不存在返回 nil |
| ‌APPEND‌ | O(1)* | 追加字符串 | *均摊复杂度，取决于字符串长度 |
| ‌STRLEN‌ | O(1) | 获取长度 | SDS 结构直接记录长度，无需遍历 |
| ‌INCR/DECR‌ | O(1) | 原子增减 | 仅限整数值，非整数报错 |
| ‌MSET/MGET‌ | O(N) | 批量读写 | N 为 key 的数量，减少网络 RTT |
| ‌SETNX‌ | O(1) | 不存在则设 | 分布式锁常用，等价于 SET ... NX |
| ‌GETSET‌ | O(1) | 设新值返旧值 | 6.2+ 建议用 SET ... GET 替代 |

应用
缓存：利用Redis的高性能读写能力，将数据库查询结果、热点配置等数据存入Redis，大幅降低数据库压力。
验证码：依托Redis的自动过期特性，实现短信、图形验证码的安全存储与校验。
Token：基于Redis实现分布式环境下的用户身份令牌管理，保障多服务节点的令牌一致性。
Session：解决分布式集群下的Session共享问题，让多台服务器的用户登录状态完全同步。
计数器：利用Redis的原子自增命令，实现高并发场景下的访问量、点赞数、限流计数，完全避免线程安全问题。
库存：基于Redis的原子操作实现高性能库存扣减，应对秒杀、大促等高流量场景。

### Hash
Redis Hash（哈希）类型是一个键值对集合，特别适合存储对象。它允许你将一个对象的多个字段（Field）和值（Value）存储在同一个 Key 下，相比 String 类型序列化整个对象，Hash 能更灵活地单独修改或获取某个字段。

‌HSET：将哈希表 key 中的字段 field 的值设为 value
HSET key field value [field value ...]

‌HGET‌
‌功能‌：获取哈希表 key 中给定字段 field 的值。
‌语法‌：HGET key field

‌HMSET‌/
‌功能‌：同时将多个 field-value 对设置到哈希表 key 中。
‌语法‌：HMSET key field value [field value ...]

HMGET‌

‌HKEYS‌
‌功能‌：获取哈希表 key 中的所有字段名（Field）。
‌语法‌：HKEYS key

‌HVALS‌
‌功能‌：获取哈希表 key 中的所有值（Value）。
‌语法‌：HVALS key

‌HLEN‌
‌功能‌：获取哈希表 key 中字段的数量。
‌语法‌：HLEN key

‌HDEL
‌功能‌：删除哈希表 key 中的一个或多个指定字段。不存在的字段将被忽略。
‌语法‌：HDEL key field [field ...]

最佳实践提示‌：
‌对象存储首选 Hash‌：如用户信息、商品属性等，方便局部更新（如只改手机号，不用重写整个用户JSON）。
‌避免大 Key‌：单个 Hash 的字段数建议控制在几千以内。如果字段过多，考虑拆分 Key 或使用 HSCAN 遍历。
‌批量操作优化‌：获取多个字段时，务必使用 HMGET 而不是循环调用 HGET。

应用：用户信息存储、对象缓存、配置中心、

### List
Redis List（列表）是一种基于‌双向链表‌（底层为 QuickList）实现的有序字符串集合。它支持从头部或尾部高效地插入和弹出元素，常被用于实现消息队列、栈、最新新闻列表等场景。

 ‌LPUSH‌/RPUSH‌
‌功能‌：将一个或多个值插入到列表的‌头部‌（左边/右边）。
‌语法‌：LPUSH/RPUSH key value [value ...]

‌LPOP‌/RPOP
‌功能‌：移除并获取列表的‌第一个‌元素（左边/右边）。
‌语法‌：LPOP key [count]

‌LRANGE‌
‌功能‌：获取列表指定范围内的元素。
‌语法‌：LRANGE key start stop

LLEN‌
‌功能‌：获取列表的长度（元素个数）。
‌语法‌：LLEN key

‌LTRIM‌
‌功能‌：对一个列表进行修剪（Trim），只保留指定区间内的元素，其余元素被删除。
‌语法‌：LTRIM key start stop

最佳实践建议
‌控制列表长度‌：如果使用 List 存储日志或动态消息，务必配合 LTRIM 使用，防止列表无限增长占用过多内存。例如：每次 LPUSH 后执行 LTRIM key 0 999 以保留最新1000条。
‌避免大范围查询‌：LRANGE 0 -1 在大列表（如超过几千个元素）上执行会阻塞 Redis 线程，生产环境中应限制返回范围或使用分页逻辑。
‌原子性组合‌：如果需要“弹出并推送到另一个列表”且保证原子性，推荐使用 RPOPLPUSH（旧版）或 LMOVE / BLMOVE（Redis 6.2+），常用于实现可靠的消息队列处理。

应用：
| 场景 | 推荐命令组合 | 关键特性 | 注意事项 |
| --- | --- | --- | --- |
| ‌消息队列‌ | LPUSH + BRPOP | 先进先出，阻塞等待 | 需处理消费失败的消息丢失问题 |
| ‌最新消息‌ | LPUSH + LRANGE + LTRIM | 头部插入，范围读取，自动截断 | 务必使用 LTRIM 限制最大长度，防止内存溢出 |
| ‌Feed 流‌ | LPUSH (推模式) | 写扩散，读极速 | 大 V 场景需结合拉模式，避免写放大 |
| ‌任务队列‌ | LPUSH + BRPOP | 原子抢占，多消费者负载均衡 | 适合轻量级异步任务，复杂调度建议用专业 MQ |

### Set
Redis Set（集合）是一个‌无序‌且‌元素唯一‌的字符串集合。其底层实现通常是哈希表（Hash Table），这使得添加、删除和查找操作的时间复杂度均为 O(1)。

‌去重性‌：集合中不允许存在重复元素。如果向集合中添加已存在的成员，操作会被忽略，集合内容不变。
‌无序性‌：集合中的元素没有固定的顺序，每次获取所有成员时，返回的顺序可能不同。
‌高效运算‌：支持服务器端的交集、并集、差集运算，非常适合处理标签、共同好友等社交关系场景。

‌SADD‌
‌功能‌：向集合添加一个或多个成员。
‌语法‌：SADD key member [member ...]

‌SMEMBERS‌
‌功能‌：返回集合中的所有成员。
‌语法‌：SMEMBERS key

‌SREM‌
‌功能‌：移除集合中一个或多个成员。
‌语法‌：SREM key member [member ...]

‌SINTER‌ (Intersection - 交集)
‌功能‌：返回给定所有集合的交集。
‌语法‌：SINTER key [key ...]

‌SUNION‌ (Union - 并集)
‌功能‌：返回给定所有集合的并集。
‌语法‌：SUNION key [key ...]

‌SDIFF‌ (Difference - 差集)
‌功能‌：返回第一个集合与其他集合之间的差集（即在第一个集合中但不在其他集合中的元素）。
‌语法‌：SDIFF key [key ...]

‌唯一性统计‌：利用 Set 的去重特性，统计网站独立访客（UV）、文章独立阅读用户等。Key 设计如 uv:2026-07-11，每天凌晨重置或新建 Key。
‌随机抽取‌：使用 SRANDMEMBER key count 可以从集合中随机返回指定数量的元素，适用于抽奖、随机推荐场景，且不会移除原元素。
‌避免大集合运算‌：SINTER、SUNION、SDIFF 的时间复杂度与集合大小成正比。如果集合包含数百万元素，这些运算会导致 Redis 阻塞。对于超大集合，建议在客户端进行计算或使用 Bitmap/HyperLogLog 替代。

### Sorted Set
Redis Sorted Set（有序集合）在 String 基础上增加了‌分数（Score）‌字段，用于实现元素的自动排序。它是 Redis 中最强大的数据结构之一，广泛应用于排行榜、延时队列等场景。

‌ZADD‌
‌功能‌：将一个或多个成员及其分数添加到有序集合中。
‌语法‌：ZADD key [NX|XX] [CH] [INCR] score member [score member ...]

‌ZRANGE‌
‌功能‌：返回有序集合中指定索引区间内的成员，‌按分数从低到高‌排序。
‌语法‌：ZRANGE key start stop [WITHSCORES] [BYSCORE|BYLEX] [REV] [LIMIT offset count]

‌ZREVRANGE‌
‌功能‌：返回有序集合中指定索引区间内的成员，‌按分数从高到低‌排序。
‌直接替代：ZRANGE key start stop REV // REV 反向排序

‌ZSCORE‌
‌功能‌：返回有序集合中指定成员的分数。
‌语法‌：ZSCORE key member

‌ZINCRBY‌
‌功能‌：为有序集合中指定成员的分数加上增量 increment。
‌语法‌：ZINCRBY key increment member

‌ZRANK‌
‌功能‌：返回有序集合中指定成员的排名（索引），‌按分数从低到高‌排序。
‌语法‌：ZRANK key member [WITHSCORE]

‌ZREM‌
‌功能‌：移除有序集合中的一个或多个成员。
‌语法‌：ZREM key member [member ...]

‌排行榜实现‌：
使用 ZADD 录入用户分数。
使用 ZREVRANGE key 0 9 WITHSCORES 获取前 10 名。
使用 ZREVRANK key user_id 获取某用户的具体排名（注意排名从 0 开始，展示时需 +1）。
‌延时队列‌：
将消息作为 Member，将“执行时间戳”作为 Score。
使用 ZRANGEBYSCORE key 0 current_timestamp LIMIT 0 1 获取到期的任务。
处理完成后使用 ZREM 移除。
‌避免大 Value‌：虽然 ZSet 性能优秀，但单个 Key 下的成员数建议控制在几万以内。若数据量极大，应考虑分片存储或使用专门的搜索引擎/数据库。

### Bitmap
Redis Bitmap（位图）并非一种独立的数据类型，而是基于 String 类型的二进制位操作扩展。它通过操作二进制位的 0 和 1 来记录状态，核心优势在于‌极致的空间节省‌和‌高效的统计能力‌。
‌SETBIT‌
‌功能‌：对 key 所储存的字符串值，设置或清除指定偏移量（offset）上的位（bit）。
‌语法‌：SETBIT key offset value

‌GETBIT‌
‌功能‌：获取 key 所储存的字符串值中，指定偏移量上的位值。
‌语法‌：GETBIT key offset

‌BITCOUNT‌
‌功能‌：统计字符串被设置为 1 的 bit 数。
‌语法‌：BITCOUNT key [start end]

应用：
签到
海量用户状态统计
用户行为去重与标记
布隆过滤器底层支持

注意事项与最佳实践
‌Offset 限制‌：Bitmap 的最大长度为 2^32位（约 512MB）。因此，作为 offset 的用户 ID 必须是整数，且不能过大。如果用户 ID 是不连续的稀疏大整数（如 UUID 转换后的巨大数字），会造成巨大的空间浪费。
‌优化‌：建议维护一个用户 ID 到紧凑整数索引的映射关系，或者确保用户 ID 是从 1 开始连续递增的。
‌大 Key 风险‌：虽然 Bitmap 节省空间，但如果 offset 极大（如设置为 SETBIT key 1000000000 1），Redis 会分配大量内存来填充中间的 0，导致瞬间内存飙升甚至阻塞。务必控制 offset 的最大值。
‌位运算扩展‌：除了上述命令，Redis 还提供 BITOP（对多个 Bitmap 进行 AND/OR/XOR/NOT 运算），可用于复杂的多维度用户圈选（如：找出“昨天活跃”且“今天未活跃”的用户）。

### HyperLogLog
hyperLogLog‌ 是 Redis 提供的一种用于‌基数统计‌（Cardinality Estimation）的概率型数据结构。
它的核心目标是：‌用极小的内存（固定约 12KB）统计海量数据的去重数量‌，允许有极小的误差（标准误差为 0.81%）。

‌PFADD‌
‌功能‌：将指定元素添加到 HyperLogLog 结构中。
‌语法‌：PFADD key element [element ...]

PFCOUNT
‌功能‌：返回给定 HyperLogLog 的基数估算值（即去重后的元素数量）。
‌语法‌：PFCOUNT key [key ...]

PFMERGE
功能‌：将多个 HyperLogLog 合并为一个。
‌语法‌：PFMERGE destkey sourcekey [sourcekey ...]

应用：
网站/APP 独立访客统计
搜索引擎去重统计
广告曝光去重

最佳实践与注意事项
‌不可逆性‌：HyperLogLog ‌不支持删除元素‌（没有 PFREM 命令）。如果业务需要支持取消签到或移除用户，HyperLogLog 不适用，需改用 Set 或 Bitmap。
‌误差接受度‌：确认业务是否能接受 0.81% 的误差。对于财务、库存等需要精确计数的场景，‌严禁‌使用 HyperLogLog。
‌合并优化‌：如果需要频繁统计多个时间段的总和（如“最近7天 UV”），建议每天凌晨通过 PFMERGE 将前一天的数据合并到一个长期 Key 中，或者定期合并周/月数据，以减少 PFCOUNT 多 key 合并时的计算开销。
‌内存固定‌：即使只添加了 1 个元素，HyperLogLog 也会占用约 12KB 内存。因此，‌不适合小规模数据去重‌（如少于几千个元素），此时 Set 更节省内存且精确。

### Geo
Redis GEO（地理空间）功能基于 ‌Sorted Set (ZSet)‌ 实现，将经纬度转换为 GeoHash 整数作为 Score 存储。

‌GEOADD‌
‌功能‌：将指定的地理空间位置（纬度、经度、名称）添加到指定的 key 中。
‌语法‌：GEOADD key longitude latitude member [longitude latitude member ...]

‌GEODIST‌
‌功能‌：返回两个给定位置之间的距离。
‌语法‌：GEODIST key member1 member2 [unit]

‌GEOSEARCH‌ (新版，Redis 6.2+)
‌功能‌：更灵活地搜索指定范围内的成员，支持以“成员”或“经纬度”为中心，支持矩形或圆形搜索。
‌语法‌：
GEOSEARCH key 
  FROMMEMBER member | FROMLONLAT longitude latitude 
  BYRADIUS radius m|km|mi|ft | BYBOX width height m|km|mi|ft 
  [WITHCOORD] [WITHDIST] [WITHHASH] 
  [COUNT count [ANY]] 
  [ASC|DESC]

最佳实践与注意事项
精度限制‌：Redis GEO 使用 52 位整数存储 GeoHash，经纬度精度约为 ‌0.6 米‌。对于超高精度定位（如厘米级测绘）不适用。
‌纬度限制‌：有效纬度范围为 ‌-85.05112878 到 85.05112878‌。超出此范围（如南北极附近）无法添加。
‌性能优化‌：
GEORADIUS / GEOSEARCH 的时间复杂度与搜索半径覆盖的元素数量成正比。如果半径过大（如覆盖全球），性能会急剧下降。
建议结合 COUNT 限制返回数量，或在应用层缩小搜索范围。
‌数据存储‌：GEO 数据本质是 ZSet，可以使用 ZREM 删除位置，使用 ZRANGE 查看原始 GeoHash 分数，但不建议直接操作底层 ZSet 命令，以免破坏地理索引结构。
‌集群支持‌：在 Redis Cluster 中，GEO 数据的 Key 必须经过哈希槽分配。如果涉及多 Key 的复杂运算，需确保 Key 落在同一节点或使用哈希标签

### Stream
Redis Stream 是 Redis 5.0 引入的‌专业消息队列‌数据结构。
它解决了 List 无法实现消息持久化、消费确认（ACK）和消费者组（Consumer Group）等痛点，功能对标 Kafka。

‌XADD‌
‌功能‌：向流中添加新消息。
‌语法‌：XADD key [NOMKSTREAM] [MAXLEN|MINID threshold] *|id field value [field value ...]

XREAD‌
‌功能‌：读取流中的消息，支持阻塞等待。
‌语法‌：XREAD [COUNT count] [BLOCK milliseconds] STREAMS key [key ...] id [id ...]

‌XGROUP‌
‌功能‌：创建、管理消费者组。
常用子命令‌：
XGROUP CREATE key groupname id [MKSTREAM]：创建组。id 设为 $ 表示从最新消息开始消费；设为 0 表示从头开始。
XGROUP DESTROY key groupname：删除组。
XGROUP DELCONSUMER key groupname consumername：删除组内的特定消费者。

‌XACK‌
‌功能‌：确认消息已被成功处理。
‌语法‌：XACK key groupname id [id ...]
‌逻辑‌：
在消费者组模式中，消息被读取后会进入 ‌PEL (Pending Entries List)‌ 状态。
只有执行 XACK 后，消息才会从 PEL 中移除，标记为“已完成”。
‌若未 ACK‌：消息会一直留在 PEL 中，其他消费者无法再次获取，除非通过 XPENDING 发现并重新分配。

‌XPENDING‌
‌功能‌：查看正在处理中（已读取但未 ACK）的消息。
‌语法‌：
XPENDING key groupname：简要统计（总 pending 数、最小/最大 ID、消费者列表）。
XPENDING key groupname - + count [consumername]：详细列出具体 pending 的消息 ID、所属消费者、空闲时间（Idle time）。
‌应用场景‌：‌故障恢复‌。如果某个消费者宕机，其处理中的消息会一直 Pending。
监控系统可通过 XPENDING 发现空闲时间过长的消息，并将其重新分配给其他健康消费者（配合 XCLAIM 命令）。

Stream 消息生命周期总结
‌生产‌：XADD 写入消息。
‌消费‌：XREADGROUP 从组中读取消息，消息进入 ‌PEL‌（Pending 状态）。
‌处理‌：业务逻辑处理消息。
‌确认‌：处理成功后执行 XACK，消息从 PEL 移除。
‌异常处理‌：若消费者宕机未 ACK，通过 XPENDING 发现，使用 XCLAIM 将消息转移给其他消费者重试。

最佳实践建议
‌必须设置 MAXLEN‌：使用 XADD ... MAXLEN ~ 10000 限制流长度，避免内存爆炸。
‌务必执行 XACK‌：在业务逻辑成功执行后才调用 XACK，确保消息不丢失。
‌监控 PEL‌：定期通过 XPENDING 监控积压消息，设置报警阈值，防止消费者宕机导致消息堆积无法被重新消费。


### stream & kafka
选择 Redis Stream 的场景：轻量级、低延迟任务：如实时通知、小规模的异步打卡任务、Webhooks 转发。
拒绝过度架构（YAGNI）：团队规模小，项目中已经在使用 Redis 做缓存，
且数据量不超过亿级，不想为了一个队列去额外维护一套沉重的 Kafka 集群。
数据允许丢弃或生命周期极短：处理完（XACK）之后，可以用 XDEL 或 XTRIM 直接释放内存，不需要保留历史记录。

选择 Apache Kafka 的场景：跨团队的数据总线：作为公司级别的 Event Backbone，
十几个微服务都要过来订阅同一份数据（如用户的行为日志）。
大数据与流计算：需要配合 Flink、Spark Streaming 做复杂的滑动窗口计算、实时大屏报表。
日志审计与事件溯源（Event Sourcing）：金融交易、操作审计等需要将过去几个月甚至几年的消息永久、安全地保存在磁盘上，
允许随时“时光倒流”重新回放（Replay）的场景。

# redis 持久化
Redis 并非绝对不会丢数据，它能在绝大多数场景下保障数据安全，核心依赖其内置的‌RDB快照‌和‌AOF日志‌两大持久化机制，以及进阶的混合持久化模式。

### RDB
RDB是Redis的全量内存快照机制，它会在指定时间点，将内存中所有数据以‌压缩二进制格式‌完整写入磁盘，生成后缀为.rdb的快照文件。
1. 核心命令
‌save‌：由主进程直接执行快照生成，全程阻塞所有业务请求，大内存实例会导致服务长时间不可用，生产环境几乎不使用。
‌bgsave‌：主进程fork出独立子进程，由子进程完成快照写入，主进程全程不阻塞，是生产环境生成RDB的标准方式。
2. 生成时机
手动触发：执行save或bgsave命令。
自动触发：配置save 900 1这类规则（900秒内至少1次写操作就触发）、主从全量同步、执行shutdown且未开启AOF时自动生成。
3. fork过程
主进程调用系统fork()创建子进程，此时父子进程共享同一份内存页表。利用Linux的‌写时复制（COW）‌机制，主进程后续处理新写请求时，才会复制被修改的内存页，既避免阻塞业务，又大幅降低内存额外开销。
5. 优缺点
‌优点‌：文件体积小，重启加载速度极快，适合做全量冷备和灾难恢复。
‌缺点‌：两次快照间的增量数据完全不保存，极端场景下可能丢失数分钟数据；大内存实例fork子进程时会产生短暂停顿。
6. 恢复场景
Redis启动时自动检测到.rdb文件，优先加载其中的全量数据到内存，完成后即可对外提供服务。如果同时开启AOF，Redis会优先加载AOF文件（因为AOF数据更完整）。

### AOF
AOF是Redis以追加日志形式记录所有写操作的持久化方案，相比RDB能大幅缩小数据丢失窗口。

核心配置项
appendonly‌
控制AOF功能的总开关，配置为appendonly yes开启，no关闭。开启后Redis会将每条写命令以协议格式追加到AOF日志文件中。

‌appendfsync
控制AOF缓冲区数据同步到磁盘的策略，直接决定数据安全性和性能表现，对应三个模式：
‌always‌：每执行一条写命令就立即同步磁盘，几乎不丢数据，但IO压力极大，性能骤降。
‌everysec‌（默认推荐）：每秒执行一次磁盘同步，平衡性能与安全性，极端断电场景下最多丢失1秒数据。
‌no‌：完全交由操作系统内核调度同步，性能最高，但丢数据风险完全不可控。

AOF重写（rewrite）
当日志文件体积持续膨胀时，Redis会触发后台重写机制：子进程基于当前内存的最新数据，生成一份精简的新AOF文件，剔除冗余无效命令（比如多次修改同一个key只保留最终状态），大幅压缩文件体积，避免日志无限增长。

恢复流程
Redis启动时优先检测AOF文件是否存在：若存在，逐条重放文件中记录的所有写命令，完整还原内存数据；若AOF文件损坏，会尝试自动修复，修复失败则拒绝启动，需人工校验处理。

### RDB vs AOF
| 对比维度 | RDB | AOF |
| --- | --- | --- |
| 数据安全性 | 低，可能丢失快照间隔内数据 | 高，默认配置最多丢失1秒数据 |
| 文件体积 | 小，压缩后远小于AOF | 大，记录所有操作易膨胀 |
| 恢复速度 | 极快，直接加载快照 | 慢，需逐条重放所有命令 |
| 性能开销 | 低，仅fork子进程生成快照 | 高，持续的磁盘IO写入 |

Redis 4.0+支持混合持久化，将RDB全量快照和AOF增量日志结合，兼顾恢复速度与数据安全，是当前生产环境的主流配置。

# Redis事务
Redis 事务（Transaction）是一组命令的集合，允许客户端一次性执行多个命令。与关系型数据库不同，‌Redis 事务不支持回滚‌，且不具备原子性隔离（即事务中的命令不会立即执行，而是排队等待）。

### 事务控制
‌MULTI‌
‌功能‌：标记一个事务块的开始。
‌逻辑‌：执行 MULTI后，后续发出的命令不会立即执行，而是被放入一个‌队列‌中暂存。
```
MULTI
# 返回 OK
SET key1 "value1"
# 返回 QUEUED
INCR key2
# 返回 QUEUED
```

‌EXEC‌
‌功能‌：执行事务块内所有排队的命令。
‌逻辑‌：
按入队顺序依次执行所有命令。
即使其中某条命令执行失败（如类型错误），其他命令仍会继续执行（‌无回滚机制‌）。
如果在 MULTI 之前使用了 WATCH，且被监控的键在事务执行前被修改，则整个事务会被放弃，返回 (nil)。
‌返回值‌：包含每个命令执行结果的数组。

‌DISCARD‌
‌功能‌：取消事务，清空事务队列。
‌逻辑‌：
丢弃所有已排队但未执行的命令。
如果使用了 WATCH，会自动解除对所有键的监控。
‌应用场景‌：当发现入队命令有误，或业务逻辑需要中止事务时调用。

### 乐观锁控制
‌WATCH‌
‌功能‌：监视一个或多个键，实现‌乐观锁‌（Optimistic Locking）。
‌逻辑‌：
在 MULTI 之前执行。
如果在 EXEC 执行之前，被监视的键被其他客户端修改（包括删除、过期、重写值），则 EXEC 会失败，返回 (nil)，事务不执行。
如果键未被修改，事务正常执行。
‌应用场景‌：解决并发竞争问题，如库存扣减、余额转账等需要“检查-设置”原子性的场景。

‌UNWATCH‌
‌功能‌：取消对所有键的监视。
‌逻辑‌：
通常在事务执行成功或失败后自动触发，但也可手动调用以提前解除监控。
如果事务已执行（EXEC）或已取消（DISCARD），监控也会自动解除。

### redis事务和mysql事务的对比
| 特性 | Redis 事务 | MySQL/PG 事务 |
| --- | --- | --- |
| ‌原子性‌ | ‌不完全支持‌。命令排队执行，中间出错不回滚。 | 完全支持。任何步骤失败均整体回滚。 |
| ‌隔离性‌ | ‌无隔离‌。事务执行期间，其他命令可穿插执行。 | 支持多种隔离级别（如 RR, RC）。 |
| ‌持久性‌ | 依赖 RDB/AOF 配置。 | 依赖 Binlog/Redo Log。 |
| ‌并发控制‌ | 通过 WATCH 实现乐观锁。 | 通过行锁/表锁实现悲观锁或 MVCC。 |

### 最佳实践与注意事项
‌无回滚机制‌：Redis 设计哲学是“简单快速”。如果事务中某条命令语法正确但逻辑错误（如对 String 执行 List 操作），Redis 记录错误并继续执行后续命令。‌业务层需自行处理部分失败的情况‌。
‌WATCH 性能‌：WATCH 是高开销操作，因为它需要服务器维护键的版本监控。在高并发场景下，大量使用 WATCH 可能导致性能下降。
‌替代方案‌：
对于简单的原子操作优先使用单命令原子性（如 INCR, SETNX, LPUSH）。
对于复杂逻辑，推荐使用 ‌Lua 脚本‌（EVAL）。Lua 脚本在 Redis 中原子执行，且支持条件判断和循环，比 MULTI/EXEC + WATCH 更高效、更灵活。
‌网络往返‌：使用管道（Pipeline）配合事务可以减少网络 RTT，提高批量操作效率。
