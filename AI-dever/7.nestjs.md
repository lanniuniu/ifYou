# NestJS基础
### NestJS 整体架构
NestJS 是一个用于构建高效、可扩展的 Node.js 服务器端应用程序的框架。它完全使用 TypeScript 编写，并保留了 JavaScript 的兼容性。其整体架构设计深受 ‌Angular‌ 启发，核心设计思想是提供一套‌开箱即用的应用架构‌，解决 Node.js 生态中项目结构松散、难以维护的问题。
1. 核心设计哲学：结构化与解耦
NestJS 的核心目标是为企业级应用提供标准化的架构模式，主要基于以下三大编程范式：
‌面向对象编程 (OOP)‌：利用类、接口、继承等特性，构建清晰的数据结构和业务逻辑单元。
‌函数式编程 (FP)‌：支持纯函数和高阶函数，增强代码的可测试性和不可变性。
‌响应式编程 (RP)‌：内置对 RxJS 的支持，便于处理异步数据流和复杂的事件驱动场景。
‌底层抽象‌：
NestJS 本身不是一个 HTTP 服务器，而是一个建立在现有 HTTP 框架（默认 ‌Express‌，可选 ‌Fastify‌）之上的抽象层。它暴露底层平台的 API，使得开发者既能享受 NestJS 的结构化优势，又能直接使用底层平台丰富的第三方中间件和生态系统。
2. 标准架构分层（4+2 模型）
NestJS 遵循严格的关注点分离原则，通常采用“4层核心 + 2层扩展”的分层架构：
- 核心4层：请求处理主干
| 层级 | 组件 | 核心职责 | 边界约束 |
| --- | --- | --- | --- |
| ‌控制层‌ | ‌Controller‌ | 接收 HTTP 请求，处理路由匹配，参数校验，返回响应。 | ‌只处理 HTTP 相关逻辑‌（如状态码、Header）。严禁包含业务逻辑或数据库操作。 |
| ‌服务层‌ | ‌Service‌ | 封装核心业务逻辑，协调数据流转，处理事务。 | ‌只关注业务规则‌。不直接操作 SQL，不感知 HTTP 细节。通过依赖注入调用 Repository。 |
| ‌数据访问层‌ | ‌Repository/DAO‌ | 负责数据库 CRUD 操作，ORM 映射，原生查询。 | ‌只负责数据持久化‌。不包含业务判断逻辑。 |
| ‌实体层‌ | ‌Entity/Model‌ | 定义数据库表结构映射，字段类型及关系。 | ‌纯数据结构‌。无行为逻辑，仅作为数据载体。 |
- 扩展2层：切面增强
| 层级 | 组件 | 核心职责 | 执行时机 |
| --- | --- | --- | --- |
| ‌中间件层‌ | ‌Middleware‌ | 请求预处理：日志记录、跨域设置、Body 解析、基础鉴权。 | 在路由匹配之前执行，无法访问具体的 Controller 上下文。 |
| ‌管道/守卫/拦截器‌ | ‌Pipe/Guard/Interceptor‌ | ‌Pipe‌：参数转换与验证。‌Guard‌：权限鉴定（如 JWT 校验）。‌Interceptor‌：响应格式化、执行时长统计、异常捕获。 | 在 Controller 执行前后介入，具有更强的上下文感知能力。 |
3. 请求生命周期与执行链路
当一个 HTTP 请求进入 NestJS 应用时，会经过以下严格的执行顺序：
‌Incoming Request‌：客户端发起请求。
‌Middleware‌：全局或路由绑定的中间件执行（如日志、CORS）。
‌Guards‌：守卫检查请求是否有权限访问该路由（如身份认证）。
‌Interceptors (Pre)‌：前置拦截器执行（如请求计时开始）。
‌Pipes‌：管道对路由参数进行转换和验证（如将字符串 ID 转为数字，校验 DTO）。
‌Controller‌：控制器方法被执行，调用相应的 Service。
‌Service‌：业务逻辑处理，可能调用 Repository 操作数据库。
‌Repository/Entity‌：数据持久化操作，返回结果给 Service。
‌Interceptors (Post)‌：后置拦截器执行（如格式化响应数据、记录耗时）。
‌Outgoing Response‌：最终响应发送回客户端。
‌注意‌：如果在任何阶段发生错误，请求将直接跳转到 ‌Exception Filters‌ 进行统一异常处理。
4. 核心机制：依赖注入 (DI) 与模块化
- 依赖注入容器 (IoC Container)
NestJS 内置了一个强大的 IoC 容器，自动管理组件的生命周期和依赖关系。 IOC:控制反转容器
‌元数据收集‌：通过 TypeScript 装饰器（如 @Injectable, @Controller）和 reflect-metadata 库，在编译阶段收集类的依赖信息。
‌自动解析‌：运行时，容器根据依赖拓扑图自动实例化对象并注入所需的服务。这使得单元测试变得极其简单，只需替换 Mock 对象即可。
- 模块化系统 (Module System)
NestJS 应用由多个模块组成，每个模块是一个带有 @Module() 装饰器的类。
‌有向无环图 (DAG)‌：模块之间的依赖关系构成一个 DAG。启动时，NestJS 会通过拓扑排序确定模块的初始化顺序。
‌高内聚低耦合‌:
controllers: 该模块拥有的控制器。
providers: 该模块创建并由 IoC 容器实例化的服务（可被其他模块导入）。
imports: 该模块依赖的其他模块。
exports: 该模块希望共享给其他模块的服务。
5. 为什么选择 NestJS 架构？
‌强制规范‌：通过 CLI 生成标准文件结构，避免团队因个人喜好导致的项目结构混乱。
‌易于测试‌：依赖注入使得每个组件都可以独立于外部环境进行测试。
‌可扩展性‌：模块化设计允许轻松拆分微服务或懒加载模块。
‌类型安全‌：基于 TypeScript，从编译阶段即可发现大部分类型错误，提升大型项目的维护性。

总结来说，NestJS 的整体架构是一个‌基于依赖注入和模块化设计的、分层清晰的、面向企业级开发的服务端框架‌。它通过抽象底层 HTTP 细节，让开发者专注于业务逻辑的实现，同时保证了代码的可维护性和可扩展性。

### 为什么选择 NestJS？
NestJS 的核心价值在于‌“架构规范”‌与‌“企业级可维护性”‌。

‌解决 Node.js 生态的碎片化问题‌：Node.js 原生或轻量框架（如 Express/Koa）不强制规定项目结构，导致大型项目随着团队扩大变得难以维护（“面条代码”）。NestJS 提供了开箱即用的标准架构（类似 Angular/Spring Boot）。
‌TypeScript 原生支持‌：从底层设计就完全拥抱 TypeScript，提供强大的类型安全和智能提示，显著降低大型项目的重构风险。
‌依赖注入（DI）系统‌：内置强大的 IoC 容器，使得组件之间的耦合度极低，极大提升了代码的可测试性（Unit Test）和可复用性。
‌平台无关性‌：NestJS 是一个抽象层，底层可以切换 HTTP 适配器（默认 Express，可选 Fastify），甚至支持微服务传输层（TCP, Redis, gRPC, MQTT 等），无需重写业务逻辑。

### 与 Express、Koa、Fastify 的区别
NestJS 不是一个底层的 HTTP 服务器，而是一个‌构建在现有 HTTP 框架之上的框架‌。
| 特性 | Express | Koa | Fastify | NestJS |
| --- | --- | --- | --- | --- |
| ‌定位‌ | 极简 Web 框架 | 极简、中间件框架 | 高性能 Web 框架 | ‌企业级应用框架‌ |
| ‌架构风格‌ | 无约束，自由度高 | 无约束，异步友好 | 无约束，插件化 | ‌强制模块化、分层架构‌ |
| ‌性能‌ | 中等 | 中等 | ‌极高‌ (基准测试领先) | 取决于底层适配器 (Express/Fastify) |
| ‌依赖管理‌ | 手动 require/import | 手动 require/import | 手动 require/import | ‌自动依赖注入 (DI)‌ |
| ‌适用场景‌ | 小型项目、快速原型、API | 中间件密集型应用 | 高吞吐、低延迟场景 | ‌中大型复杂业务、微服务、团队协作项目‌ |
| ‌关系‌ | - | - | - | ‌NestJS 默认使用 Express，也可配置为 Fastify‌ |

‌与 Express 区别‌：Express 是库，NestJS 是框架。Express 需要你决定如何组织代码，NestJS 告诉你如何组织。
‌与 Koa 区别‌：Koa 更轻量，强调异步流程控制（Async/Await），但同样缺乏架构约束。NestJS 的拦截器（Interceptor）概念借鉴了 Koa 的洋葱模型，但更加结构化。
‌与 Fastify 区别‌：Fastify 专注极致性能。NestJS 可以通过 @nestjs/platform-fastify 适配器使用 Fastify 作为底层，从而在保持 NestJS 架构优势的同时获得 Fastify 的性能。

### MVC 架构
NestJS 遵循经典的 MVC 模式，但进行了更细致的分层：
‌Controller (C)‌：负责处理 HTTP 请求和响应。只关注路由匹配、参数提取和状态码返回。‌不包含业务逻辑‌。
‌Service (M - Logic)‌：负责核心业务逻辑。它是 MVC 中的“Model”逻辑部分，协调数据流，调用数据访问层。
‌Repository/Entity (M - Data)‌：负责数据库交互和数据模型定义。
‌View (V)‌：NestJS 通常用于构建 API，因此很少涉及传统 View。如果需要渲染页面，可以使用模板引擎（如 Handlebars, Pug），但这不是 Nest 的重点。

###  模块化开发 (Modularity)
NestJS 应用由多个模块组成，每个模块是一个带有 @Module() 装饰器的类。
‌高内聚‌：相关的 Controller、Service、Provider 放在同一个 Module 中。
‌低耦合‌：模块之间通过 imports 和 exports 进行通信。
@Module({
  imports: [DatabaseModule], // 依赖的其他模块
  controllers: [UserController], // 本模块的控制器
  providers: [UserService], // 本模块的服务（提供者）
  exports: [UserService] // 导出给其他模块使用的服务
})
export class UserModule {}

### Metadata（元数据）与 Decorator（装饰器）
NestJS heavily 依赖 TypeScript 的装饰器和反射机制来收集元数据。
‌Decorator (装饰器)‌：
是一种特殊类型的声明，可以被附加到类、方法、访问器、属性或参数上。
在 Nest 中，装饰器用于定义路由、注入依赖、定义模块等。
例如：@Controller('users')、@Get()、@Injectable()、@Inject()。

‌Metadata (元数据)‌：
TypeScript 编译器可以将装饰器中的信息编译为元数据。
NestJS 使用 reflect-metadata 库在运行时读取这些元数据。
‌工作流程‌：
你写 @Controller('users')。
TypeScript 编译后，会在 UserController 类上存储元数据 { path: 'users' }。
NestJS 启动时，扫描所有带 @Controller 的类，读取元数据，注册路由表。
你写 constructor(private userService: UserService)。
TypeScript 存储元数据 { type: UserService }。
NestJS 读取元数据，知道这个构造函数需要 UserService 的实例，于是从容器中查找并注入。

### CLI使用
‌Schematics‌ 是 Nest CLI 背后的代码生成引擎（由 Angular 团队开发，NestJS 复用并扩展了它）。
‌工作原理‌：Schematics 定义了文件生成的模板和规则。当你运行 nest g controller 时，CLI 会查找 @nestjs/schematics 包中对应的 Controller 模板，根据你提供的名称替换变量，并将文件写入磁盘。
‌自定义‌：企业级项目中，团队可以编写自定义的 Schematics 集合，以强制执行特定的内部代码规范或目录结构。
‌优势‌：
‌一致性‌：确保所有开发者生成的代码结构完全相同。
‌效率‌：减少手动创建文件和编写样板代码的时间。
‌集成‌：生成的代码自动更新模块引用（如自动将新 Service 添加到 Module 的 providers 中）。

### 为什么必须分离？核心设计哲学
1. 单一职责原则 (Single Responsibility Principle, SRP)
每个组件只负责一件事，且把它做好：
‌Controller‌：只负责 ‌HTTP 交互层‌。处理路由匹配、请求参数解析、状态码返回、Header 设置。它不关心数据怎么查，只关心“用户发了什么”和“我要回什么”。
‌Service‌：只负责 ‌业务逻辑层‌。处理数据计算、事务控制、第三方 API 调用。它不关心数据是通过 HTTP 还是 MQTT 传来的，只关心“业务规则是否正确”。
‌Module‌：只负责 ‌组织与依赖关系‌。定义哪些服务属于这个模块，哪些控制器暴露给外部，以及依赖其他什么模块。它是应用的“组装说明书”。
2. 解耦与可测试性 (Decoupling & Testability)
‌独立单元测试‌：
你可以单独测试 UserService 的业务逻辑，无需启动 HTTP 服务器，只需 Mock 掉 Repository。
你可以单独测试 UsersController 的参数验证和响应格式，只需 Mock 掉 UserService。
如果代码混在一起（如 Controller 直接查数据库），测试时必须连接数据库或模拟整个 HTTP 栈，极大增加测试复杂度。
‌依赖倒置‌：Controller 依赖的是 Service 的‌接口/抽象‌，而不是具体实现。这使得未来替换底层逻辑（如从 MySQL 切换到 MongoDB）时，Controller 无需任何修改。
3. 可维护性与团队协作 (Maintainability)
‌清晰的文件定位‌：当需要修改“用户注册逻辑”时，开发者知道直接去 users.service.ts；当需要修改“注册接口 URL”时，去 users.controller.ts。
‌避免冲突‌：在大型团队中，前端对接人员可能只改 Controller，后端逻辑人员只改 Service，减少代码合并冲突。

### 项目目录架构
| 组件 | 文件示例 | 核心职责 | 严禁行为 |
| --- | --- | --- | --- |
| ‌Controller‌ | users.controller.ts | 1. 定义路由 (@Get, @Post)2. 接收请求参数 (@Body, @Param)3. 调用 Service4. 返回响应数据 | 1. 禁止写 SQL 或数据库操作2. 禁止写复杂业务判断（如 if-else 业务规则）3. 禁止直接操作文件系统 |
| ‌Service‌ | users.service.ts | 1. 实现核心业务逻辑2. 协调多个 Repository3. 处理事务 (Transaction)4. 调用第三方服务 | 1. 禁止感知 HTTP 细节（如 Request/Response 对象）2. 禁止直接返回 HTTP 状态码（应抛出异常或返回数据） |
| ‌Module‌ | users.module.ts | 1. 声明本模块的 Controllers 和 Providers2. 导入依赖的其他模块 (imports)3. 导出供其他模块使用的服务 (exports) | 1. 禁止包含业务逻辑2. 禁止直接实例化类（由 DI 容器管理） |

### 生命周期
##### 应用启动阶段 (Bootstrap Phase)
这一阶段发生在 main.ts 执行 await app.listen() 时，主要完成依赖图的构建和模块的组装。
1. Bootstrap & Module 初始化
‌入口‌：NestFactory.create(AppModule)。
‌核心动作‌：
‌依赖图解析‌：NestJS 扫描 AppModule 及其导入的所有子模块（如 UsersModule）。
‌拓扑排序‌：根据模块间的 imports 关系，确定模块的初始化顺序（解决循环依赖问题）。
‌元数据收集‌：读取所有 @Module, @Controller, @Injectable 装饰器的元数据。
2. Provider 初始化 (关键修正点)
‌顺序‌：‌Provider 先于 Controller 被实例化‌（或至少同时准备就绪）。
‌原因‌：Controller 的构造函数通常依赖 Service（Provider）。IoC 容器必须先创建好 Service 实例，才能将其注入到 Controller 中。
‌生命周期钩子‌：
若 Provider 实现了 OnModuleInit，此时触发 onModuleInit()。
这是执行数据库连接、缓存预热等初始化逻辑的最佳时机。
3. Controller 初始化
‌动作‌：IoC 容器实例化 Controller，并将已准备好的 Provider 注入其构造函数。
‌路由注册‌：NestJS 扫描 Controller 中的 @Get, @Post 等装饰器，将路由路径映射到具体的处理方法，并绑定中间件、守卫、管道等增强器。
4. Application Ready
‌标志‌：所有模块初始化完成，HTTP 服务器（Express/Fastify）开始监听端口。
‌生命周期钩子‌：
触发全局及所有 Provider 的 OnApplicationBootstrap 接口方法 onApplicationBootstrap()。
此时应用已完全就绪，可执行启动后的后台任务（如消息队列消费者订阅）。

##### 请求处理阶段 (Request Lifecycle)
当应用运行后，每个 HTTP 请求都会经过以下严格的管道。这是 NestJS ‌“洋葱模型”‌的核心体现。
1. Incoming Request
客户端发起 HTTP 请求。
2. Middleware (中间件)
‌执行时机‌：路由匹配之前。
‌职责‌：日志记录、CORS 处理、Body 解析、基础鉴权。
‌特点‌：无法访问具体的 Controller 上下文，是最外层的拦截。
3. Guards (守卫)
‌执行时机‌：中间件之后，管道之前。
‌职责‌：权限鉴定（如 JWT 验证、角色检查 @Roles('admin')）。
‌决策‌：若返回 false 或抛出异常，请求直接终止，不会进入后续环节。
4. Interceptors (前置拦截器)
‌执行时机‌：守卫通过之后，管道之前。
‌职责‌：请求转换、缓存检查、执行计时开始。
‌特点‌：可以修改请求流，或在后续步骤完成后执行后置逻辑（类似 AOP）。
5. Pipes (管道)
‌执行时机‌：调用 Controller 方法之前。
‌职责‌：
  ‌转换‌：将原始请求数据（如字符串 ID）转换为目标类型（如数字、DTO 对象）。
  ‌验证‌：使用 class-validator 校验 DTO 数据结构。若验证失败，直接抛出 400 错误。
6. Controller (控制器)
‌执行‌：调用具体的路由处理方法。
‌动作‌：接收经过管道处理的数据，调用注入的 ‌Service‌。
7. Service (服务层)
‌执行‌：处理核心业务逻辑，调用 Repository 操作数据库或第三方 API。
‌返回‌：将处理结果返回给 Controller。
8. Interceptors (后置拦截器)
‌执行‌：Controller 执行完毕后。
‌职责‌：响应数据格式化（如统一包裹 { code: 200, data: ... }）、记录请求耗时、清理资源。
9. Exception Filters (异常过滤器)
‌触发条件‌：上述任何环节抛出未捕获异常。
‌职责‌：捕获异常，转换为标准的 HTTP 错误响应（如 500 Internal Server Error），避免暴露堆栈信息。
10. Outgoing Response
最终生成的 HTTP 响应发送回客户端。

##### 应用销毁阶段 (Destroy Phase)
当应用接收到终止信号（如 SIGTERM）或调用 app.close() 时触发。
1. OnModuleDestroy
触发所有 Provider 的 onModuleDestroy() 方法。
用于清理模块级别的资源（如关闭特定的数据库连接池）。
2. OnApplicationShutdown
触发所有 Provider 的 onApplicationShutdown() 方法。
用于优雅停机（Graceful Shutdown）：停止接收新请求，等待现有请求处理完毕，关闭服务器连接，释放内存资源。

##### 钩子
| 接口 | 方法 | 触发时机 | 典型用途 |
| --- | --- | --- | --- |
| OnModuleInit | onModuleInit() | 模块依赖解析完成后 | 数据库连接初始化、配置加载 |
| OnApplicationBootstrap | onApplicationBootstrap() | 应用完全启动后 | 启动后台任务、消息队列订阅 |
| OnModuleDestroy | onModuleDestroy() | 模块销毁前 | 关闭特定资源连接 |
| OnApplicationShutdown | onApplicationShutdown() | 应用关闭前 | 优雅停机、清理全局资源 |

### 总结
选择 NestJS 是因为它在 Node.js 世界中引入了‌严谨的工程化标准‌。它通过 ‌IOC/DI‌ 解耦组件，通过 ‌Module‌ 组织代码，通过 ‌Decorator/Metadata‌ 简化配置，通过 ‌Middleware/Guard/Pipe/Interceptor‌ 标准化请求处理流程。虽然对于简单脚本来说它显得厚重，但对于需要长期维护、多人协作的大型后端系统，它是目前 Node.js 生态中的最佳实践之一。

# NestJS核心概念
### module
@Module 装饰器确实是 NestJS 组织代码的基石。它不仅仅是一个文件容器，更是 ‌IoC 容器的配置清单‌，定义了依赖关系的边界。
##### @Module() 核心属性解析
@Module() 元数据对象包含四个关键属性，它们共同决定了模块的行为和可见性：
1. imports（导入其他模块）
‌作用‌：声明当前模块所依赖的其他模块。
‌机制‌：只有被 imports 的模块中 ‌exports 数组‌里列出的 Provider，才能被当前模块的 Controller 或 Service 注入使用。
‌注意‌：导入一个模块并不意味着能使用该模块的所有服务，只能使用其“公开”的部分。
2. controllers（注册控制器）
‌作用‌：声明属于本模块的 Controller 类。
‌机制‌：NestJS 启动时会扫描此数组，将这些 Controller 中的路由（@Get, @Post 等）注册到全局路由表中。
‌约束‌：Controller 必须且只能在所属模块的 controllers 数组中声明，否则路由无效。
3. providers（提供服务/依赖）
‌作用‌：声明由 IoC 容器实例化并管理的类（Service, Repository, Guard, Pipe 等）。
‌机制‌：这些类在本模块内部可用。当其他类（如 Controller）在构造函数中请求依赖时，容器从此列表中查找并注入单例实例。
‌范围‌：默认情况下，Provider 仅在当前模块内可见。
4. exports（导出 Provider）
‌作用‌：定义本模块对外“公开”的服务子集。
‌机制‌：若模块 B 想使用模块 A 中的 UserService，模块 A 必须在 exports: [UserService] 中显式导出它，且模块 B 需在 imports: [AModule] 中导入模块 A。
‌封装性‌：未在 exports 中声明的 Provider 被视为模块的“私有实现”，外部无法访问，实现了良好的封装。

##### 五种核心模块类型详解
根据用途和作用域的不同，NestJS 模块可分为以下五类：
1. Feature Module（功能模块）
‌定义‌：围绕特定业务功能组织的模块，是应用的主要组成部分。
‌示例‌：UsersModule, OrdersModule, ProductsModule。
‌特点‌：
包含该功能所需的 Controller, Service, Entity, DTO。
通常被 AppModule 或其他高层模块导入。
‌最佳实践‌：每个功能模块应保持高度内聚，尽量减少对其他功能模块的直接依赖。
2. Shared Module（共享模块）
‌定义‌：封装常用工具、通用服务或第三方库包装器的模块，供多个功能模块复用。
‌示例‌：SharedModule 包含 LoggerService, ValidationPipe, HttpHelper。
‌特点‌：
在 exports 中导出通用 Provider。
被多个 Feature Module 通过 imports 引入。
‌注意‌：避免在 SharedModule 中放置业务逻辑，它应只包含无状态或通用状态的逻辑。
3. Core Module（核心模块）
‌定义‌：包含应用启动所需的全局配置、基础设置或单例服务的模块。
‌示例‌：CoreModule 包含数据库连接配置、全局异常过滤器、全局守卫、ConfigService。
‌特点‌：
通常只在根模块 AppModule 中导入一次。
可能包含 forRoot() 静态方法用于异步配置。
‌区别‌：与 SharedModule 不同，Core Module 通常不旨在被广泛复用，而是作为应用的“基础设施层”。
4. Dynamic Module（动态模块）
‌定义‌：允许在运行时动态配置和注册 Provider 的模块。这是 NestJS 最强大的特性之一。
‌场景‌：
数据库连接配置需从环境变量读取。
第三方库（如 TypeORM, Mongoose, ConfigModule）需要根据用户传入的参数生成不同的 Provider。
5. Global Module（全局模块）
‌定义‌：一旦导入，其导出的 Provider 在整个应用中处处可用，无需在其他模块的 imports 中重复声明。
‌实现‌：使用 @Global() 装饰器。
typescript
@Global()
@Module({
  providers: [ConfigService],
  exports: [ConfigService],
})
export class ConfigModule {}
‌场景‌：适用于几乎每个模块都需要使用的服务，如配置服务、日志服务、认证服务。
‌警告‌：
‌减少魔法‌：过度使用全局模块会导致依赖关系不明确，增加调试难度。
‌最佳实践‌：仅在确实需要全局访问且频繁使用时才设为全局，优先通过显式 imports 管理依赖。

##### 总结
‌Module 是边界‌：它定义了代码的组织单元和依赖可见性。
‌Imports/Exports 是接口‌：通过显式的导入和导出，实现了模块间的松耦合。
‌动态/全局是增强‌：Dynamic Module 提供运行时灵活性，Global Module 提供便捷的全局访问，但需谨慎使用以保持架构清晰。

### Controller
Controller 是处理 HTTP 请求的入口点。它的核心职责是‌接收请求‌并‌返回响应‌，而不包含复杂的业务逻辑。

##### 类级别装饰器：@Controller()
1. 基本定义
@Controller() 装饰器用于定义一个类为 NestJS 的控制器。它告诉 NestJS 这个类负责处理传入的 HTTP 请求。
2. 路由前缀（Path Prefix）
‌作用‌：为控制器中的所有路由方法设置公共前缀。
‌示例‌：

```typescript
@Controller('users') // 所有路由以 /users 开头
export class UsersController {
  @Get() // 映射到 GET /users
  findAll() {}
  
  @Get(':id') // 映射到 GET /users/:id
  findOne(@Param('id') id: string) {}
}
```
‌最佳实践‌：通常使用资源名称的复数形式作为前缀（如 users, products），符合 RESTful 规范。

##### 方法级别装饰器：HTTP 动词映射
这些装饰器将特定的 HTTP 方法映射到类的处理方法上。NestJS 提供了以下标准装饰器：
1. @Get()
‌用途‌：处理 ‌GET‌ 请求，用于‌获取‌资源。
‌特点‌：幂等性，不应改变服务器状态。
‌示例‌：
```typescript
@Get()
findAll(): string {
  return 'This action returns all users';
}
```
2. @Post()
‌用途‌：处理 ‌POST‌ 请求，用于‌创建‌新资源。
‌特点‌：非幂等，每次调用可能产生不同结果（如生成新 ID）。
‌示例‌：
```typescript
@Post()
create(@Body() createUserDto: CreateUserDto): string {
  return 'This action adds a new user';
}
```
3. @Put()
‌用途‌：处理 ‌PUT‌ 请求，用于‌全量更新‌资源。
‌特点‌：幂等。客户端需提供资源的完整表示，缺失字段可能被重置或忽略。
‌示例‌：
```typescript
@Put(':id')
update(@Param('id') id: string, @Body() updateUserDto: UpdateUserDto): string {
  return `This action updates a #${id} user`;
}
```
4. @Patch()
‌用途‌：处理 ‌PATCH‌ 请求，用于‌部分更新‌资源。
‌特点‌：非幂等（取决于实现）。客户端只需提供需要更改的字段。
‌区别‌：与 PUT 相比，PATCH 更灵活，适合只修改个别字段的场景。
‌示例‌：
```typescript
@Patch(':id')
updatePartial(@Param('id') id: string, @Body() updateDto: any): string {
  return `This action partially updates a #${id} user`;
}
```
5. @Delete()
‌用途‌：处理 ‌DELETE‌ 请求，用于‌删除‌资源。
‌特点‌：幂等。删除不存在的资源通常返回 404 或 204（无内容）。
‌示例‌：
```typescript
@Delete(':id')
remove(@Param('id') id: string): string {
  return `This action removes a #${id} user`;
}
```
6. @All()
‌用途‌：处理‌所有类型‌的 HTTP 请求（GET, POST, PUT, DELETE 等）。
‌场景‌：
调试或测试接口。
构建代理中间件。
处理 Webhook（当来源方使用不同动词时）。
‌警告‌：在生产环境中应谨慎使用，因为它模糊了 API 的语义，不符合 RESTful 最佳实践。
‌示例‌：
```typescript
@All()
handleAll(): string {
  return 'This action handles all request methods';
}
```

### 核心概念：请求参数提取
Controller 方法不仅映射路由，还负责从请求中提取数据。NestJS 提供了专门的装饰器来简化这一过程：
| 装饰器 | 来源 | 用途 |
| --- | --- | --- |
| @Request() / @Req() | req 对象 | 获取原生 Express/Fastify 请求对象 |
| @Response() / @Res() | res 对象 | 获取原生响应对象（慎用，会禁用自动序列化） |
| @Param() | URL 路径参数 | 获取路由中的动态参数（如 /users/:id 中的 id） |
| @Body() | 请求体 | 获取 POST/PUT/PATCH 请求中的 JSON 数据 |
| @Query() | 查询字符串 | 获取 URL 问号后的参数（如 /users?limit=10 中的 limit） |
| @Headers() | 请求头 | 获取 HTTP Header 信息 |
| @Ip() | IP 地址 | 获取客户端 IP |
```typescript
@Get(':id/profile')
getProfile(
  @Param('id') id: string,
  @Query('details') details: boolean,
  @Headers('authorization') token: string
) {
  return { id, details, token };
}
```

##### 最佳实践与注意事项
‌保持 Controller 轻量‌：
Controller 只负责‌参数提取‌、‌调用 Service‌ 和‌返回响应‌。
‌严禁‌在 Controller 中编写数据库查询、复杂计算或业务判断逻辑。这些应移至 Service 层。
‌使用 DTO 进行验证‌：

配合 @Body() 使用 DTO（Data Transfer Object）类和 class-validator 库，确保输入数据的结构和类型正确。
NestJS 的 ‌ValidationPipe‌ 会自动处理验证失败并返回 400 错误。
‌统一响应格式‌：

虽然可以直接返回对象，但建议通过 ‌Interceptor‌ 或全局过滤器统一包装响应格式（如 { code: 200, data: ..., message: 'Success' }），
而不是在每个 Controller 方法中手动包装。
‌RESTful 语义一致性‌：

严格遵循 HTTP 动词的语义：GET 查，POST 增，PUT/PATCH 改，DELETE 删。
避免在 GET 请求中执行写操作，或在 POST 请求中执行纯查询。

##### 总结
Controller 是 NestJS 应用与外部世界交互的‌网关‌。
‌@Controller('prefix')‌ 定义资源集合。
‌@Get/Post/Put/Patch/Delete‌ 定义对资源的具体操作。
‌参数装饰器‌ (@Body, @Param 等) 负责将 HTTP 协议数据转换为 TypeScript 对象。
通过将这些职责严格限制在 Controller 层，并将业务逻辑下沉至 Service 层，你能够构建出清晰、可测试且易于维护的 API 接口。
