- table
‌主键（Primary Key）‌：唯一标识表中每一行数据的列，不能为空且不能重复（通常是 id）。
‌外键（Foreign Key）‌：用于建立表与表之间关联的列，指向另一张表的主键。

```
// 创建表
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY AUTO_INCREMENT, // 自增主键
    username VARCHAR(255) NOT NULL, // 非空
    email VARCHAR(255) UNIQUE, // 唯一 可以为空
    age INT
)

// 插入数据
INSERT INTO users (username, email, age) 
VALUES ('alice', 'alice@example.com', 25);

// 查询
SELECT * FROM users WHERE age > 20;

-- 添加新列
ALTER TABLE users ADD COLUMN phone VARCHAR(20);

-- 修改列类型
ALTER TABLE users MODIFY COLUMN age SMALLINT;

// 删除表
DROP TABLE users;

// 注释
COMMENT ""
```

- 索引
分类：数据结构&物理存储&逻辑约束
按逻辑约束分类：主键索引、唯一索引、普通索引、组合索引、其他高级索引
| 索引类型 | 适用场景 | 注意事项 |
| --- | --- | --- |
| ‌主键索引‌ | 几乎每张表必备 | 尽量选择短小、自增的整数类型 |
| ‌唯一索引‌ | 业务上不能重复的字段（如手机号、订单号） | 区分于主键，允许为空 |
| ‌普通/组合索引‌ | 高频查询的 WHERE、JOIN、ORDER BY 字段 | 遵循最左前缀原则，避免过多索引影响写性能 |
| ‌全文索引‌ | 大文本搜索 | 替代 LIKE %...% |
‌不要过度索引‌：每个索引都会降低写操作的速度，并占用磁盘空间。
‌区分度高优先‌：选择区分度高的列（如身份证、邮箱）建立索引，性别（只有男/女）建立索引意义不大。
‌覆盖索引优化‌：如果查询的列都在索引中，无需回表，性能极佳。

- 约束(Constraint)
分类：实体完整性约束、参照完整性约束、域完整性约束
```
CREATE TABLE employees (
    id INT AUTO_INCREMENT PRIMARY KEY,          -- 主键约束
    email VARCHAR(100) NOT NULL UNIQUE,         -- 非空 + 唯一约束
    department_id INT,
    salary DECIMAL(10, 2) DEFAULT 0.00,         -- 默认值约束

        FOREIGN KEY (department_id) 
        REFERENCES departments(id)
);
```

# SQL 查询
- WHERE
- LIKE
LIKE 是 SQL 中用于‌模糊匹配字符串‌的运算符，通常配合 WHERE 子句使用，通过通配符来搜索符合特定模式的数据。
%: 匹配任意数量的字符（包括零个字符）
_: 匹配单个字符
索引失效‌：当 LIKE 以 % 开头时（如 '%keyword'），MySQL 无法使用索引，MySQL InnoDB 引擎的普通索引，
    B+Tree 索引的最左前缀匹配原则‌。会导致全表扫描，性能极差。
优化建议‌：如果业务需要频繁做后缀模糊搜索，可考虑使用全文索引（FULLTEXT）或 Elasticsearch 等搜索引擎。
如果待搜索的字符串本身包含 % 或 _，需要使用 ESCAPE 关键字指定转义符
-- 查找包含“50%”字样的记录
SELECT * FROM products WHERE discount_info LIKE '%50\%%' ESCAPE '\';

- DISTINCT
DISTINCT 是 SQL 中用于‌去除查询结果中重复行‌的关键字。
DISTINCT 必须紧跟 SELECT 之后、字段名之前使用
在 DISTINCT 中，多个 NULL 值被视为‌相同‌，最终只保留一个 NULL。
‌先过滤再去重‌：大数据量场景下，先用 WHERE 缩小数据范围，再执行 DISTINCT，避免全表扫描。

- GROUP BY
GROUP BY 是 SQL 中用于‌将数据按指定列分组，并结合聚合函数进行统计计算‌的核心子句。
SQL 的执行顺序是：WHERE → GROUP BY → HAVING → ORDER BY。
```

```
HAVING和WHERE区别：
WHERE是过滤数据，HAVING是过滤分组后的聚合函数结果

- UNION
UNION 可以将两个或多个 SELECT 查询的结果纵向拼接成一个结果集，但要求各查询的‌列数相同‌且对应列的‌数据类型兼容‌。
```
SELECT column1, column2 FROM table1
UNION
SELECT column1, column2 FROM table2;
```
UNION 与 UNION ALL 的关键区别
UNION： 会去重，由于需要扫描比较每一行来判断是否重复，执行速度相对较慢。
UNION ALL 不会去重。省去了去重和排序的额外开销，处理大数据时性能优势明显。

# 多表查询
- INNER JOIN
用于‌横向关联‌两个或多个表的核心操作，它只返回两个表中‌匹配条件完全一致‌的行。
```
SELECT A.name, B.order_date // A B 是别名
FROM users A
INNER JOIN orders B ON A.id = B.user_id; // ON 关键字 是连接条件
```
索引优化‌：确保 ON 子句中的关联列（如 user_id）在两张表中都建立了索引，否则会导致全表扫描（笛卡尔积），性能极差。
‌小表驱动大表‌：虽然 MySQL 优化器会自动调整，但理解连接顺序有助于编写更高效的 SQL。

- LEFT JOIN & RIGHT JOIN
LEFT JOIN（左外连接）是 SQL 中用于‌保留左表所有记录‌的关联操作。即使右表中没有匹配的行，左表的记录也会出现在结果中，右表对应的字段则显示为 NULL。
```
SELECT A.name, B.order_date
FROM users A
LEFT JOIN orders B ON A.id = B.user_id; // ON 关键字 是连接条件
```
索引至关重要‌：确保 ON 子句中的右表关联列（如 user_id）有索引，否则每次匹配都需要全表扫描右表，性能极差。
‌过滤条件位置‌：如果对右表的过滤条件写在 WHERE 中，LEFT JOIN 可能会退化为 INNER JOIN。若需保留左表所有行且过滤右表，应将条件写在 ON 子句中。
RIGHT JOIN 是 镜像写法，逻辑完全一致
永远使用 LEFT JOIN‌：即使逻辑上需要右连接，也通过交换表顺序改写为 LEFT JOIN。
‌代码可读性优先‌：团队协作中，统一使用 LEFT JOIN 能大幅降低代码审查和排错的时间成本。

- CROSS JOIN
‌交叉连接‌，它会产生两个表的‌笛卡尔积‌。
结果是两者行数的乘积
```
-- 语法一：显式使用 CROSS JOIN
SELECT A.name, B.color
FROM users A
CROSS JOIN colors B; // 不需要 ON 关键字
```
‌数据膨胀风险‌：两张 1000 行的表做 CROSS JOIN，结果集瞬间达到 100 万行。大表之间直接交叉连接极易导致数据库崩溃或内存溢出。
‌务必先过滤‌：如果确实需要交叉连接，应先用子查询或 CTE 缩小表的数据范围，再进行组合。

- Self JOIN
自连接‌并不是一种新的连接语法，而是‌同一张表自己连接自己‌的特殊用法，本质上是 INNER JOIN 或 LEFT JOIN 的一种应用场景。
```
SELECT
    e.name AS 员工姓名,
    m.name AS 上级姓名
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
```
别名必须‌：不使用别名会导致 SQL 无法区分两个实例，引发语法错误。

- 子查询
嵌套在另一个 SQL 语句（如 SELECT、INSERT、UPDATE、DELETE）内部的 SELECT 查询。它也被称为‌内部查询‌或‌嵌套查询‌。
子查询的结果通常作为外层查询的条件或数据源，用于解决‌需要多步逻辑‌的复杂查询问题。它必须用括号 () 包裹。
IN、EXISTS 和 NOT EXISTS 是子查询中常用的‌条件判断运算符‌，用于检查主查询的行是否存在于子查询的结果集中。
IN: 判断某个值是否‌等于‌子查询返回结果集中的任意一个值。
EXISTS: 只判断子查询是否‌至少返回一行‌，不关心具体值。一旦找到匹配行就立即返回 TRUE，停止扫描。
NOT EXISTS: 与 EXISTS 相反，子查询‌没有返回任何行‌时才为 TRUE。

‌能用 JOIN 替代尽量用 JOIN‌：在大多数情况下，MySQL 优化器对 JOIN 的优化远好于子查询，尤其是 IN 子查询可能被优化为 EXISTS 或直接关联。
‌避免大表关联子查询‌：大表使用关联子查询会导致外层每行都执行一次子查询，性能极差。
‌EXISTS 替代 IN‌：当子查询结果集很大时，EXISTS 通常比 IN 效率更高。

# 数据库设计
- 三大范式
第一范式：列不可再分。一列只存一个值，不存复合数据
第二范式：消除部分依赖。在满足 1NF 的基础上，‌非主键字段必须完全依赖于主键‌，而不能只依赖主键的一部分。
第三范式：消除传递依赖。在满足 2NF 的基础上，非主键字段不能间接依赖于主键‌，即不允许存在传递依赖。
三大范式递进关系：1NF（原子性）→ 2NF（消除部分依赖）→ 3NF（消除传递依赖）
实际设计建议：
‌不必过度追求范式化‌：有时为了查询性能，会有意保留一些冗余字段（反范式化），这需要在数据一致性与查询效率之间做权衡。
‌优先满足 3NF‌：大多数业务场景下，达到第三范式已经足够，既能保证数据完整性，又不会过度拆分表导致查询复杂。

- 主键设计
问：主键为什么不用 UUID？
答：性能问题。1.破坏 B+Tree 索引有序性 2.存储空间浪费 3.深分页性能灾难 4.排序与范围查询失效
   /5. 替代方案：如果业务确实需要分布式全局唯一 ID，推荐使用‌雪花算法（Snowflake）‌生成的 64 位有序 ID，它既保证了全局唯一，又保留了时间戳的有序性，完美适配 InnoDB 的 B+Tree 索引特性。

问：主键为什么不是INT.
BIGINT 既保留了数值型主键的‌有序、紧凑、高效‌优势，又提供了足够的‌容量冗余，是 MySQL 主键的“黄金标准”‌。

- 外键
为什么互联网公司很少使用？
答：1. 高并发性能瓶颈 2. 分布式架构下失效 3.影响迭代与数据迁移 4.引发级联风险
 5.替代方案：互联网公司普遍将数据一致性逻辑‌下沉到业务代码‌中实现，配合事务、MQ消息补偿等机制，既规避了外键的性能和架构限制，也能灵活适配复杂的分布式业务场景。

- 字段设计
能用数字别用字符串
能用短的别用长的
尽量 NOT NULL‌：NULL 值占用额外空间且影响索引效率
‌设置默认值
‌大字段拆出去

- 软删除
数据可恢复‌	误删后可以通过 UPDATE deleted_at = NULL 恢复，避免生产事故
‌数据可追溯‌	保留完整的历史数据，方便审计、统计、排查问题
‌避免级联风险‌	不用外键，软删除天然规避了级联删除导致的数据灾难
‌业务需求‌	很多业务需要"撤回删除"，如订单取消、账号注销后可恢复

什么时候用物理删除？
‌日志表/流水表‌：数据量巨大且无需恢复，如操作日志。
‌敏感数据‌：如用户密码历史，按法规要求必须彻底删除。
‌定时清理‌：软删除数据定期归档后再物理删除。

# 索引
- 定义
索引是一种‌有序的数据结构‌（如 B+Tree），存储在磁盘上，将原表的数据按照索引列的值‌排序存储‌，并记录每个值对应的数据行位置。
为什么快？
MySQL InnoDB 默认使用 ‌B+Tree‌ 作为索引结构。3-4次io 即可。
‌核心结论‌：索引将查找复杂度从 ‌O(n)‌ 降到 ‌O(log n)‌，数据量越大，优势越明显。
缺点：写入变慢、占用存储空间‌、‌过多索引拖累写入性能‌

| ✅ 建议建索引 | ❌ 不建议建索引 |
| --- | --- |
| WHERE 频繁使用的列 | 频繁更新的列 |
| JOIN 关联的列 | 区分度低的列（如性别） |
| ORDER BY 排序的列 | 数据量太少的表（< 1000 行） |
| 唯一值多的列（如手机号） | TEXT/BLOB 大字段 |

- B+Tree

| 索引类型 | 等值查询 | 范围查询 | 排序 | 磁盘 IO | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| ‌B+Tree‌ ⭐ | ✅ | ✅ | ✅ | ‌极低（3~4次）‌ | ‌MySQL 默认，通用场景‌ |
| B Tree | ✅ | ⚠️ 差 | ⚠️ 差 | 中等 | 几乎不用 |
| Hash | ✅ 极快 | ❌ | ❌ | 低 | 仅内存数据库（Redis） |
| 红黑树 | ✅ | ✅ | ✅ | ‌高（20次）‌ | 内存数据结构（Java Map） |

- 聚簇索引
‌聚簇索引 = 主键索引 = 叶子节点存的就是整行数据，找到索引就找到了数据，不用回表。‌

- 二级索引
InnoDB 中除聚簇索引外所有普通索引的统称，它的核心特点是：‌叶子节点不存整行数据，只存主键值，查询时需要先找到主键，再回聚簇索引拿完整数据‌。

- 回表
慢的核心原因是它需要多走一次完整的聚簇索引B+Tree查找，产生额外的磁盘IO开销‌。
优化方案
最有效的方式是使用‌覆盖索引‌，将查询需要的所有字段都加入二级索引，直接从索引中拿到全部数据，完全跳过回表步骤。

- 覆盖索引
快的核心原因是它完全跳过了回表步骤，省去了第二次聚簇索引B+Tree查找的磁盘IO开销‌。
创建覆盖索引：将查询语句中 WHERE、SELECT、ORDER BY 涉及的所有字段，全部包含在同一个索引中‌。
CREATE INDEX idx_cov_optimized ON orders(status, created_at, order_id, total);

- 联合索引
联合索引（Composite Index）‌ 是在表的多个列上共同创建的一个B+Tree索引，是MySQL多条件查询场景下最核心的性能优化手段
联合索引的匹配严格遵循最左前缀规则，
与覆盖索引的区别
| 对比维度 | 联合索引 | 覆盖索引 |
| --- | --- | --- |
| 本质 | 物理索引结构 | 查询优化效果 |
| 核心作用 | 支持多条件快速过滤，遵循最左前缀原则 | 消除回表，减少磁盘IO |
| 依赖条件 | 多列共同创建索引 | 任意索引（单列/联合）都可能成为覆盖索引 |
| 性能收益 | 避免全表扫描，加速多条件查询 | 省去第二次聚簇索引查找，IO直接减半 |

联合索引是覆盖索引最常用的载体

- 索引失效
违背“最左前缀”原则（联合索引）
对索引列做“加工”（计算或函数）
类型隐式转换（字符串不加引号）
模糊查询通配符在前
OR 连接条件未全覆盖索引

特殊情况：优化器主动放弃索引
数据量占比过大
字符集不一致‌
统计信息过时‌

如何排查索引失效
使用 EXPLAIN 查看执行计划，重点关注以下字段：
| 字段 | 正常走索引 | 索引失效/全表扫描 |
| --- | --- | --- |
| ‌type‌ | ref, range, eq_ref | ALL (全表扫描) |
| ‌key‌ | 显示具体的索引名 | NULL |
| ‌Extra‌ | Using index (覆盖索引) | Using where (需回表或全表扫) |

- Explain
EXPLAIN 是 MySQL 提供的用于分析 SQL 查询执行计划的核心工具。
EXPLAIN SELECT * FROM users WHERE name = '张三';
| 字段 | 含义 | 关键关注点 |
| --- | --- | --- |
| ‌type‌ | 访问类型 | ‌性能由好到差‌：system > const > eq_ref > ref > range > index > ALL⚠️ 出现 ALL 表示全表扫描，必须优化。 |
| ‌key‌ | 实际使用的索引 | 显示优化器最终选择使用的索引名。若为 NULL，说明没走索引。 |
| ‌rows‌ | 预估扫描行数 | 数值越小越好。若过大，说明索引区分度低或未生效。 |
| ‌Extra‌ | 额外信息 | ‌重点关注‌：✅ Using index：覆盖索引，极快❌ Using filesort：需要额外排序，慢❌ Using temporary：使用临时表，慢❌ Using where：需回表或全表过滤 |
| ‌possible_keys‌ | 可能用到的索引 | 列出所有候选索引。若为 NULL 但 key 不为空，说明优化器选了其他更优索引。 |
| ‌key_len‌ | 索引使用长度 | 判断联合索引是否被完全使用。长度越短，说明使用的索引列越少。 |

- EXPLAIN ANALYZE
增强版的 EXPLAIN，它不仅展示优化器的‌预估计划‌，还会‌实际执行 SQL‌并返回真实的运行时统计信息，是定位性能瓶颈的终极利器。
