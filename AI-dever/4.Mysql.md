### table
‌主键（Primary Key）‌：唯一标识表中每一行数据的列，不能为空且不能重复（通常是 id）。
‌外键（Foreign Key）‌：用于建立表与表之间关联的列，指向另一张表的主键。
‌索引（Index）‌：类似于书籍的目录，用于加速数据查询速度。
```
// 创建表
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY AUTO_INCREMENT, // 自增主键
    username VARCHAR(255) NOT NULL, // 非空
    email VARCHAR(255) UNIQUE, // 唯一 可以为空
    age INT
)

// 插入数据
INSERT INTO users (username, email, age) 
VALUES ('alice', 'alice@example.com', 25);

// 查询
SELECT * FROM users WHERE age > 20;

-- 添加新列
ALTER TABLE users ADD COLUMN phone VARCHAR(20);

-- 修改列类型
ALTER TABLE users MODIFY COLUMN age SMALLINT;

// 删除表
DROP TABLE users;

// 注释
COMMENT ""
```

分类：数据结构&物理存储&逻辑约束

| 索引类型 | 适用场景 | 注意事项 |
| --- | --- | --- |
| ‌主键索引‌ | 几乎每张表必备 | 尽量选择短小、自增的整数类型 |
| ‌唯一索引‌ | 业务上不能重复的字段（如手机号、订单号） | 区分于主键，允许为空 |

### 约束(Constraint)
分类：实体完整性约束、参照完整性约束、域完整性约束
```
CREATE TABLE employees (
    id INT AUTO_INCREMENT PRIMARY KEY,          -- 主键约束
    email VARCHAR(100) NOT NULL UNIQUE,         -- 非空 + 唯一约束
    department_id INT,
    salary DECIMAL(10, 2) DEFAULT 0.00,         -- 默认值约束

        FOREIGN KEY (department_id) 
        REFERENCES departments(id)
);
```

LIKE 是 SQL 中用于‌模糊匹配字符串‌的运算符，通常配合 WHERE 子句使用，通过通配符来搜索符合特定模式的数据。

如果待搜索的字符串本身包含 % 或 _，需要使用 ESCAPE 关键字指定转义符

### DISTINCT

HAVING和WHERE区别：

### UNION
UNION 可以将两个或多个 SELECT 查询的结果纵向拼接成一个结果集，但要求各查询的‌列数相同‌且对应列的‌数据类型兼容‌。
```
SELECT column1, column2 FROM table1
UNION
SELECT column1, column2 FROM table2;
```
UNION 与 UNION ALL 的关键区别
UNION： 会去重，由于需要扫描比较每一行来判断是否重复，执行速度相对较慢。
UNION ALL 不会去重。省去了去重和排序的额外开销，处理大数据时性能优势明显。

# 多表查询
### INNER JOIN
用于‌横向关联‌两个或多个表的核心操作，它只返回两个表中‌匹配条件完全一致‌的行。
```
SELECT A.name, B.order_date // A B 是别名
FROM users A
INNER JOIN orders B ON A.id = B.user_id; // ON 关键字 是连接条件
```
索引优化‌：确保 ON 子句中的关联列（如 user_id）在两张表中都建立了索引，否则会导致全表扫描（笛卡尔积），性能极差。
‌小表驱动大表‌：虽然 MySQL 优化器会自动调整，但理解连接顺序有助于编写更高效的 SQL。

### LEFT JOIN & RIGHT JOIN
LEFT JOIN（左外连接）是 SQL 中用于‌保留左表所有记录‌的关联操作。即使右表中没有匹配的行，左表的记录也会出现在结果中，右表对应的字段则显示为 NULL。
```
SELECT A.name, B.order_date
FROM users A
LEFT JOIN orders B ON A.id = B.user_id; // ON 关键字 是连接条件
```
索引至关重要‌：确保 ON 子句中的右表关联列（如 user_id）有索引，否则每次匹配都需要全表扫描右表，性能极差。
‌过滤条件位置‌：如果对右表的过滤条件写在 WHERE 中，LEFT JOIN 可能会退化为 INNER JOIN。若需保留左表所有行且过滤右表，应将条件写在 ON 子句中。
RIGHT JOIN 是 镜像写法，逻辑完全一致
永远使用 LEFT JOIN‌：即使逻辑上需要右连接，也通过交换表顺序改写为 LEFT JOIN。
‌代码可读性优先‌：团队协作中，统一使用 LEFT JOIN 能大幅降低代码审查和排错的时间成本。

### CROSS JOIN
‌交叉连接‌，它会产生两个表的‌笛卡尔积‌。
结果是两者行数的乘积
```
-- 语法一：显式使用 CROSS JOIN
SELECT A.name, B.color
FROM users A
CROSS JOIN colors B; // 不需要 ON 关键字
```
‌数据膨胀风险‌：两张 1000 行的表做 CROSS JOIN，结果集瞬间达到 100 万行。大表之间直接交叉连接极易导致数据库崩溃或内存溢出。
‌务必先过滤‌：如果确实需要交叉连接，应先用子查询或 CTE 缩小表的数据范围，再进行组合。

### Self JOIN
自连接‌并不是一种新的连接语法，而是‌同一张表自己连接自己‌的特殊用法，本质上是 INNER JOIN 或 LEFT JOIN 的一种应用场景。
```
SELECT
    e.name AS 员工姓名,
    m.name AS 上级姓名
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
```
别名必须‌：不使用别名会导致 SQL 无法区分两个实例，引发语法错误。

### 子查询
嵌套在另一个 SQL 语句（如 SELECT、INSERT、UPDATE、DELETE）内部的 SELECT 查询。它也被称为‌内部查询‌或‌嵌套查询‌。
子查询的结果通常作为外层查询的条件或数据源，用于解决‌需要多步逻辑‌的复杂查询问题。它必须用括号 () 包裹。
IN、EXISTS 和 NOT EXISTS 是子查询中常用的‌条件判断运算符‌，用于检查主查询的行是否存在于子查询的结果集中。
IN: 判断某个值是否‌等于‌子查询返回结果集中的任意一个值。
EXISTS: 只判断子查询是否‌至少返回一行‌，不关心具体值。一旦找到匹配行就立即返回 TRUE，停止扫描。
NOT EXISTS: 与 EXISTS 相反，子查询‌没有返回任何行‌时才为 TRUE。

‌能用 JOIN 替代尽量用 JOIN‌：在大多数情况下，MySQL 优化器对 JOIN 的优化远好于子查询，尤其是 IN 子查询可能被优化为 EXISTS 或直接关联。
‌避免大表关联子查询‌：大表使用关联子查询会导致外层每行都执行一次子查询，性能极差。
‌EXISTS 替代 IN‌：当子查询结果集很大时，EXISTS 通常比 IN 效率更高。

# 数据库设计
### 三大范式
第一范式：列不可再分。一列只存一个值，不存复合数据
第二范式：消除部分依赖。在满足 1NF 的基础上，‌非主键字段必须完全依赖于主键‌，而不能只依赖主键的一部分。
第三范式：消除传递依赖。在满足 2NF 的基础上，非主键字段不能间接依赖于主键‌，即不允许存在传递依赖。
三大范式递进关系：1NF（原子性）→ 2NF（消除部分依赖）→ 3NF（消除传递依赖）
实际设计建议：
‌不必过度追求范式化‌：有时为了查询性能，会有意保留一些冗余字段（反范式化），这需要在数据一致性与查询效率之间做权衡。
‌优先满足 3NF‌：大多数业务场景下，达到第三范式已经足够，既能保证数据完整性，又不会过度拆分表导致查询复杂。

### 主键设计
问：主键为什么不用 UUID？
答：性能问题。1.破坏 B+Tree 索引有序性 2.存储空间浪费 3.深分页性能灾难 4.排序与范围查询失效
   /5. 替代方案：如果业务确实需要分布式全局唯一 ID，推荐使用‌雪花算法（Snowflake）‌生成的 64 位有序 ID，它既保证了全局唯一，又保留了时间戳的有序性，完美适配 InnoDB 的 B+Tree 索引特性。

问：主键为什么不是INT.
BIGINT 既保留了数值型主键的‌有序、紧凑、高效‌优势，又提供了足够的‌容量冗余，是 MySQL 主键的“黄金标准”‌。

### 外键
为什么互联网公司很少使用？
答：1. 高并发性能瓶颈 2. 分布式架构下失效 3.影响迭代与数据迁移 4.引发级联风险
 5.替代方案：互联网公司普遍将数据一致性逻辑‌下沉到业务代码‌中实现，配合事务、MQ消息补偿等机制，既规避了外键的性能和架构限制，也能灵活适配复杂的分布式业务场景。

### 软删除
数据可恢复‌	误删后可以通过 UPDATE deleted_at = NULL 恢复，避免生产事故

# 索引
### 定义
索引是一种‌有序的数据结构‌（如 B+Tree），存储在磁盘上，将原表的数据按照索引列的值‌排序存储‌，并记录每个值对应的数据行位置。
为什么快？
MySQL InnoDB 默认使用 ‌B+Tree‌ 作为索引结构。3-4次io 即可。
‌核心结论‌：索引将查找复杂度从 ‌O(n)‌ 降到 ‌O(log n)‌，数据量越大，优势越明显。
缺点：写入变慢、占用存储空间‌、‌过多索引拖累写入性能‌

| ✅ 建议建索引 | ❌ 不建议建索引 |
| --- | --- |
| WHERE 频繁使用的列 | 频繁更新的列 |
| JOIN 关联的列 | 区分度低的列（如性别） |
| ORDER BY 排序的列 | 数据量太少的表（< 1000 行） |
| 唯一值多的列（如手机号） | TEXT/BLOB 大字段 |

### B+Tree

| 索引类型 | 等值查询 | 范围查询 | 排序 | 磁盘 IO | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| ‌B+Tree‌ ⭐ | ✅ | ✅ | ✅ | ‌极低（3~4次）‌ | ‌MySQL 默认，通用场景‌ |
| B Tree | ✅ | ⚠️ 差 | ⚠️ 差 | 中等 | 几乎不用 |
| Hash | ✅ 极快 | ❌ | ❌ | 低 | 仅内存数据库（Redis） |
| 红黑树 | ✅ | ✅ | ✅ | ‌高（20次）‌ | 内存数据结构（Java Map） |

### 聚簇索引
‌聚簇索引 = 主键索引 = 叶子节点存的就是整行数据，找到索引就找到了数据，不用回表。‌

### 二级索引
InnoDB 中除聚簇索引外所有普通索引的统称，它的核心特点是：‌叶子节点不存整行数据，只存主键值，查询时需要先找到主键，再回聚簇索引拿完整数据‌。

### 回表
慢的核心原因是它需要多走一次完整的聚簇索引B+Tree查找，产生额外的磁盘IO开销‌。
优化方案
最有效的方式是使用‌覆盖索引‌，将查询需要的所有字段都加入二级索引，直接从索引中拿到全部数据，完全跳过回表步骤。

### 覆盖索引
快的核心原因是它完全跳过了回表步骤，省去了第二次聚簇索引B+Tree查找的磁盘IO开销‌。
创建覆盖索引：将查询语句中 WHERE、SELECT、ORDER BY 涉及的所有字段，全部包含在同一个索引中‌。
CREATE INDEX idx_cov_optimized ON orders(status, created_at, order_id, total);

### 联合索引
联合索引（Composite Index）‌ 是在表的多个列上共同创建的一个B+Tree索引，是MySQL多条件查询场景下最核心的性能优化手段
联合索引的匹配严格遵循最左前缀规则，
与覆盖索引的区别
| 对比维度 | 联合索引 | 覆盖索引 |
| --- | --- | --- |
| 本质 | 物理索引结构 | 查询优化效果 |
| 核心作用 | 支持多条件快速过滤，遵循最左前缀原则 | 消除回表，减少磁盘IO |
| 依赖条件 | 多列共同创建索引 | 任意索引（单列/联合）都可能成为覆盖索引 |
| 性能收益 | 避免全表扫描，加速多条件查询 | 省去第二次聚簇索引查找，IO直接减半 |

联合索引是覆盖索引最常用的载体

### 索引失效
违背“最左前缀”原则（联合索引）
对索引列做“加工”（计算或函数）
类型隐式转换（字符串不加引号）
模糊查询通配符在前
OR 连接条件未全覆盖索引

特殊情况：优化器主动放弃索引
数据量占比过大
字符集不一致‌
统计信息过时‌

如何排查索引失效
使用 EXPLAIN 查看执行计划，重点关注以下字段：
| 字段 | 正常走索引 | 索引失效/全表扫描 |
| --- | --- | --- |
| ‌type‌ | ref, range, eq_ref | ALL (全表扫描) |
| ‌key‌ | 显示具体的索引名 | NULL |

### Explain
EXPLAIN 是 MySQL 提供的用于分析 SQL 查询执行计划的核心工具。
EXPLAIN SELECT * FROM users WHERE name = '张三';
| 字段 | 含义 | 关键关注点 |
| --- | --- | --- |
| ‌type‌ | 访问类型 | ‌性能由好到差‌：system > const > eq_ref > ref > range > index > ALL⚠️ 出现 ALL 表示全表扫描，必须优化。 |
| ‌key‌ | 实际使用的索引 | 显示优化器最终选择使用的索引名。若为 NULL，说明没走索引。 |
| ‌rows‌ | 预估扫描行数 | 数值越小越好。若过大，说明索引区分度低或未生效。 |
| ‌Extra‌ | 额外信息 | ‌重点关注‌：✅ Using index：覆盖索引，极快❌ Using filesort：需要额外排序，慢❌ Using temporary：使用临时表，慢❌ Using where：需回表或全表过滤 |
| ‌possible_keys‌ | 可能用到的索引 | 列出所有候选索引。若为 NULL 但 key 不为空，说明优化器选了其他更优索引。 |

# 事务
### ACID
四大核心特性
| 特性 | 全称 | 核心含义 | 作用 |
| --- | --- | --- | --- |
| ‌A 原子性‌ | Atomicity | 事务是不可分割的整体，操作要么全部成功，要么全部失败回滚 | 避免部分执行导致数据不一致 |
| ‌C 一致性‌ | Consistency | 事务执行前后，数据库从一个合法状态切换到另一个合法状态，约束不被破坏 | 保证数据始终符合业务规则 |
| ‌I 隔离性‌ | Isolation | 多个并发事务互不干扰，各自操作独立执行 | 解决脏读、不可重复读、幻读等并发问题 |
| ‌D 持久性‌ | Durability | 事务提交后，数据永久写入磁盘，即使宕机也不会丢失 | 保证提交的数据绝对可靠 |

### 四种隔离级别
| 隔离级别 | 英文名称 | 脏读 | 不可重复读 | 幻读 | 性能表现 | 适用场景 |
| --- | --- | --- | --- | --- | --- | --- |
| 读未提交 | READ UNCOMMITTED | ✅ 存在 | ✅ 存在 | ✅ 存在 | 最高 | 几乎不使用 |
| 读已提交 | READ COMMITTED | ❌ 避免 | ✅ 存在 | ✅ 存在 | 较高 | 多数互联网业务（Oracle 默认） |
| 可重复读（默认） | REPEATABLE READ | ❌ 避免 | ❌ 避免 | 基本解决 | 中等 | MySQL InnoDB 默认级别 |
| 串行化 | SERIALIZABLE | ❌ 避免 | ❌ 避免 | ❌ 避免 | 最差 | 金融/强一致性场景 |

```
-- 查看当前会话隔离级别
SELECT @@transaction_isolation;

-- 修改全局隔离级别（重启后生效）
SET GLOBAL TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```
脏读：一个事务读取了另一个事务未提交的数据，由于另一个事务未提交，数据可能会回滚
幻读：一个事务前后两次读取了按相同条件范围查询的数据，但两次之间，另一个事务插入了符合条件的数据，并提交了
不可重复读：一个事务读取了另一个事务已提交的数据，如果于另一个事务更改/删除了数据，就会导致两次读取的数据不一样

- MVCC
MVCC（多版本并发控制）‌ 是 InnoDB 实现事务隔离的核心机制，它通过保存数据的历史版本，让读操作不加锁也能获取一致数据，大幅提升并发性能。
1. 核心实现三要素
MVCC 主要依靠三个组件配合工作：
‌隐藏字段‌：每行数据自动附带 DB_TRX_ID（最后修改事务ID）、DB_ROLL_PTR（回滚指针）等隐藏字段
‌Undo Log 版本链‌：数据修改时旧版本写入回滚日志，通过指针串联成链表，保存历史版本
‌Read View‌：快照读时的可见性判断规则，决定当前事务能看到哪个版本的数据
2. 可见性判断规则
Read View 包含当前活跃事务集合等信息，判断逻辑为：已提交的版本可见、活跃未提交的不可见、未来的版本不可见，以此保证快照读的一致性。
3. 核心作用
解决脏读、不可重复读等并发问题，在可重复读隔离级别下实现非阻塞读
避免读写冲突，大幅提升高并发场景下的数据库吞吐量

# 锁
### 行锁
行锁是加在‌索引记录‌上的锁。如果 SQL 语句没有用到索引，InnoDB 会退化为‌表锁‌。
仅限制其他事务对被锁行的修改或删除，不影响其他行的操作。
| 锁类型 | 锁定对象 | 主要作用 | 生效场景 |
| --- | --- | --- | --- |
| ‌Record Lock‌ | 具体的索引记录 | 防止其他事务修改/删除该行 | 精确匹配主键或唯一索引（如 WHERE id = 5） |
| ‌Gap Lock‌ | 记录之间的空隙 | 防止其他事务在空隙中‌插入‌新数据 | 范围查询（如 WHERE id > 5 AND id < 10），仅在 ‌RR隔离级别‌ 下生效 |
| ‌Next-Key Lock‌ | 记录 + 前开后闭区间 | 同时防止修改和插入，解决‌幻读 a>‌ | RR 隔离级别下的默认锁定方式（Record Lock + Gap Lock） |
‌解决并发冲突‌: 在可重复读（RR）隔离级别下，行锁配合 MVCC 解决了脏读和不可重复读；配合间隙锁解决了幻读。
‌提升并发度‌: 相比表锁，行锁允许不同事务同时更新表中的不同行。例如，事务 A 更新 id=1，事务 B 更新 id=2，两者互不阻塞。

最佳实践
务必使用索引查询‌: 确保 WHERE 条件命中索引，避免全表扫描导致锁升级。
‌尽量缩小锁定范围‌: 使用精确匹配代替范围查询，减少 Gap Lock 的范围。
‌快速提交事务‌: 持有锁的时间越短，并发冲突概率越低。

### 表锁
表锁（Table Lock）‌ 是 MySQL 中粒度最大的一种锁机制，它直接锁定整张数据表。

| 维度 | 表锁 (Table Lock) | 行锁 (Row Lock) |
| --- | --- | --- |
| ‌锁定范围‌ | 整张表 | 特定行记录 |
| ‌并发能力‌ | ‌低‌（写操作阻塞全表） | ‌高‌（不同行可并行修改） |
| ‌资源开销‌小|（实现简单，内存占用少）  |  大（需维护大量锁结构，易耗尽内存） |
| ‌加锁速度‌ | 快 | 慢 |
| ‌死锁概率‌ | 几乎无 | 较高（需配合事务隔离级别处理） |
| ‌适用引擎‌ | MyISAM、InnoDB（特定场景） | InnoDB（默认支持） |

何时使用表锁？
尽管行锁并发更高，但在以下场景表锁反而更优：
‌批量更新/删除‌：当需要修改表中大部分数据时，逐行加锁的开销远超直接锁表。
‌DDL 操作‌：如 ALTER TABLE、CREATE INDEX 等结构变更操作，通常需锁表以保证元数据一致。
‌MyISAM 引擎‌：该引擎不支持行锁，所有写操作自动升级为表锁。
‌全表扫描查询‌：若查询条件未命中索引，InnoDB 可能会升级为表锁以避免大量行锁带来的性能损耗。、

风险
阻塞严重‌：一个长时间运行的写事务持有表锁，会导致后续所有请求排队等待，甚至引发连接超时。
‌吞吐量瓶颈‌：在高并发写入场景下，表锁会成为系统性能的绝对瓶颈，TPS（每秒事务数）远低于行锁机制。

‌总结建议‌：在 InnoDB 引擎中，应优先利用索引优化查询以触发‌行锁‌，避免全表扫描导致的隐式‌表锁升级‌。仅在批量数据处理或 DDL 维护时，才主动考虑使用表锁。

### 间隙锁
间隙锁（Gap Lock）‌ 是 MySQL InnoDB 存储引擎在 ‌可重复读（Repeatable Read, RR）‌ 隔离级别下，为了防止‌幻读（Phantom Read）‌而引入的一种特殊锁机制。
| 特性 | 说明 |
| --- | --- |
| ‌目的‌ | 防止幻读，保证可重复读隔离级别的一致性 |
| ‌锁定对象‌ | 索引记录之间的空隙 |
| ‌阻塞操作‌ | 其他事务的 ‌INSERT‌ 操作 |
| ‌适用场景‌ | RR 隔离级别下的范围查询、唯一索引等值查询（非唯一索引） |
| ‌核心代价‌ | 牺牲部分并发插入性能，换取数据一致性 |

### Next-Key Lock
Next-Key Lock = ‌记录锁‌ + ‌间隙锁‌
记录锁‌：锁定索引记录本身。
‌间隙锁‌：锁定索引记录之间的“空隙”，防止其他事务在该区间插入新数据。
‌左开右闭区间‌：Next-Key Lock 锁定的范围是 （前一个索引值, 当前索引值）。
| 锁类型 | 锁定对象 | 作用 | 并发度 |
| --- | --- | --- | --- |
| ‌Record Lock‌ | 索引记录行 | 防止修改/删除该行 | 高 |
| ‌Gap Lock‌ | 索引间隙 | 防止插入新数据 | 中 |
| ‌Next-Key Lock‌ | 记录 + 间隙 | 防止修改 + 防止插入（解决幻读） | 低 |

‌一句话总结‌：Next-Key Lock 是 InnoDB 在 RR 级别下的默认锁机制，通过“锁住记录及其左侧间隙”，在保证数据一致性的同时，尽可能减少对其他事务插入操作的影响（通过退化优化）。

### 死锁
‌死锁（Deadlock）‌ 是指两个或多个事务在执行过程中，因争夺资源而造成的一种互相等待的现象。若无外力作用，它们都将无法推进下去。在 MySQL InnoDB 引擎中，死锁是并发控制中常见的问题，但通常可以通过优化设计和自动机制来解决。

MySQL 如何处理死锁？
InnoDB 引擎默认开启了死锁检测机制：

‌自动检测与回滚‌：InnoDB 会定期检测死锁。一旦发现死锁，它会选择一个“代价较小”的事务（通常是持有锁较少、修改数据较少的事务进行回滚），并抛出错误码 1213 (ER_LOCK_WAIT_TIMEOUT)。
‌牺牲者重试‌：被回滚的事务需要由应用层捕获异常后重新执行。

排查
SHOW ENGINE INNODB STATUS\G
重点关注输出中的 LATEST DETECTED DEADLOCK 部分，它会列出：
涉及的两个事务 ID
各自持有的锁和等待的锁
导致死锁的具体 SQL 语句

| 策略 | 说明 |
| --- | --- |
| ‌统一访问顺序‌ | ‌最有效方案‌。所有事务按相同的顺序（如主键 ID 从小到大）访问表或行，打破循环等待条件。 |
| ‌缩短事务粒度‌ | 事务只包含必要的核心操作，避免在事务中调用外部接口、sleep 或进行复杂计算，减少持锁时间。 |
| ‌合理加索引‌ | 确保查询走索引，避免无索引查询导致行锁升级为表锁，或产生过多的间隙锁（Gap Lock）。 |
| ‌降低隔离级别‌ | 如果业务允许，将隔离级别从 REPEATABLE-READ 降至 READ-COMMITTED，可以减少间隙锁的使用，从而降低死锁概率。 |
| ‌一次性获取锁‌ | 尽量在事务开始时一次性申请所有需要的锁，避免逐步申请。 |

### 乐观锁&&悲观锁
悲观锁‌：默认假设并发操作一定会发生冲突，在操作数据前就直接加锁，阻塞其他事务的访问，从根源上避免冲突发生。
‌乐观锁‌：默认假设并发操作很少发生冲突，操作数据时不加锁，仅在提交更新时校验数据是否被其他事务修改过，冲突时返回失败让应用层处理。
| 维度 | 悲观锁 | 乐观锁 |
| --- | --- | --- |
| 加锁时机 | 读取数据时直接加锁 | 更新提交时才校验，全程不加锁 |
| 实现方式 | 数据库原生行锁，如SELECT ... FOR UPDATE | 版本号/时间戳校验，完全由应用层实现 |
| 冲突处理 | 阻塞等待锁释放，可能产生死锁 | 发现冲突直接更新失败，需业务层重试 |
| 适用场景 | 写多读少、冲突频繁、强一致性场景（如银行转账） | 读多写少、冲突概率低、高并发场景（如商品库存、点赞） |

悲观锁实现
-- 开启事务，查询时直接加行锁
START TRANSACTION;
SELECT * FROM orders WHERE id = 1 FOR UPDATE;
-- 执行后续业务操作
UPDATE orders SET status = 2 WHERE id = 1;
COMMIT;

乐观锁实现
-- 给表添加版本号字段
ALTER TABLE orders ADD COLUMN version INT NOT NULL DEFAULT 0;
-- 更新时携带版本号校验
UPDATE orders SET status = 2, version = version + 1 
WHERE id = 1 AND version = 0;
-- 若影响行数为0，说明数据已被其他事务修改，触发重试逻辑

# 存储引擎
### InnoDB
完整支持 ACID 事务‌：通过 Undo Log 实现原子性，Redo Log 实现持久性，搭配 MVCC 实现事务隔离，操作出错可回滚，崩溃后能自动恢复数据，避免数据丢失。
‌行级锁机制‌：默认使用行级锁，高并发写入场景下多个用户可同时修改不同行，不会像 MyISAM 那样直接锁整张表，大幅降低锁冲突概率。
‌聚簇索引设计‌：数据和主键索引存储在一起，找到主键就直接拿到整行数据，主键查询性能极高，同时支持通过二级索引+覆盖索引优化查询，减少回表开销。
‌外键支持‌：原生支持外键约束，可在数据库层面保证表与表之间的数据关联合法性，避免脏数据产生。

### MyISAM
它完全不支持事务，在并发、数据可靠性、崩溃恢复等核心能力上存在致命缺陷，无法满足现代业务的基本需求‌。

### Memory
1. 核心内存组件
‌Buffer Pool（缓冲池）‌：InnoDB 最核心的内存区域，缓存表数据页和索引页，大幅减少磁盘IO，默认大小通常设为物理内存的 50%~70%。
‌Log Buffer（日志缓冲区）‌：临时存储 Redo Log，满了才刷盘，避免频繁磁盘写入，默认大小 16MB。
‌Query Cache（查询缓存）‌：MySQL 8.0 已移除，之前版本用于缓存完全相同的 SELECT 查询结果。
‌Sort Buffer（排序缓冲区）‌：执行 ORDER BY 排序时使用的内存，避免生成临时文件。

2. 关键调优要点
缓冲池命中率要保持在 ‌99% 以上‌，命中率低说明内存不足，大量数据需要从磁盘读取。
避免大事务占用过多 Log Buffer，导致频繁刷盘影响性能。
不要过度分配内存，防止操作系统发生 Swap 交换，反而让数据库性能暴跌。

### InnoDB 架构
InnoDB 主要分为两大核心模块：
‌内存池（Buffer Pool）‌：作为数据缓存层，缓存热点页、索引页、Undo/Redo 日志等，大幅降低磁盘 IO 频率
‌后台线程 + 磁盘文件‌：负责异步刷盘、事务持久化、脏页清理等底层操作

# 日志
### Redo Log
InnoDB 为了提升性能，不会每次修改都直接刷磁盘，而是先修改内存中的缓冲池（Buffer Pool），再通过 Redo Log 记录下这次修改操作。即使数据库突然宕机，重启后也能通过 Redo Log 把未刷盘的数据恢复回来，保证提交的数据绝对不丢。

流程：
事务修改数据时，先更新内存 Buffer Pool 里的数据页
把这次修改的操作细节写入 Redo Log Buffer（内存中的日志缓冲区）
事务提交时，强制把 Redo Log Buffer 里的内容刷到磁盘上的 Redo Log 文件
后台线程异步、批量地把内存中修改过的数据页刷到磁盘的表空间文件

核心参数
innodb_log_file_size：单个 Redo Log 文件的大小，默认 48MB，大事务场景建议调大到 1GB
innodb_flush_log_at_trx_commit：控制 Redo Log 刷盘策略，设为 1 时每次提交都刷盘，是 MySQL 安全级别最高的配置

核心使命：崩溃恢复能力

### Undo Log
Undo Log（回滚日志）‌ 是 InnoDB 存储引擎中用于实现事务‌原子性（Atomicity）‌和‌隔离性（Isolation）‌的核心组件。它记录了数据修改前的“旧值”，主要用于事务回滚和多版本并发控制（MVCC）。
事务回滚：当事务执行过程中发生错误，或者用户手动执行 ROLLBACK 时，数据库需要撤销已经执行的操作。
MVCC:在并发环境下，为了实现‌非锁定读‌（即读不加锁，写不阻塞读），InnoDB 利用 Undo Log 构建数据的多个历史版本。
分类
| 类型 | 触发场景 | 可见性 | 清理机制 |
| --- | --- | --- | --- |
| ‌Insert Undo Log‌ | INSERT 操作 | 仅对当前事务可见 | 事务提交后‌立即删除‌，无需后台清理 |
| ‌Update Undo Log‌ | UPDATE / DELETE 操作 | 可能被其他事务用于 MVCC 读取 | 事务提交后‌不能立即删除‌，需放入链表，由后台 ‌Purge 线程‌ 异步清理 |

为什么 Update Undo Log 不能立即删？‌
因为其他并发事务可能正在通过 MVCC 读取该数据的历史版本。只有当确认没有任何事务需要访问该历史版本时，才能安全清除。

Undo Log 和 Redo Log 的比较
| 特性 | Undo Log | Redo Log |
| --- | --- | --- |
| ‌目的‌ | 保证‌原子性‌（回滚） | 保证‌持久性‌（崩溃恢复） |
| ‌内容‌ | 逻辑日志（反向操作指令） | 物理日志（数据页变更记录） |
| ‌写入时机‌ | 事务执行过程中持续写入 | 事务提交前刷盘（WAL 机制） |
| ‌清理方式‌ | 事务提交后由 Purge 线程异步清理 | 循环写入，覆盖旧日志 |
| ‌对应 ACID‌ | Atomicity, Isolation | Durability |

 一句话总结
‌Undo Log 是 InnoDB 的“后悔药”和“时光机”：它让事务出错时能“后悔”回滚（原子性），也让并发读事务能穿越时间看到数据的历史快照（隔离性/MVCC）。

### Binlog
二进制日志是 MySQL Server 层生成的、记录所有数据变更操作的物理日志，是 MySQL 数据可靠性、主从复制、数据恢复的核心基石。

| 维度 | Binlog | Redo Log |
| --- | --- | --- |
| 所属层级 | MySQL Server 层 | InnoDB 引擎层 |
| 核心作用 | 数据恢复、主从复制 | 崩溃恢复，保证事务持久性 |
| 写入时机 | 事务提交时一次性写入 | 事务执行过程中持续写入 |
| 内容格式 | 逻辑日志，记录数据变更逻辑 | 物理日志，记录数据页的修改 |

### Relay Log
‌Relay Log（中继日志）‌ 是 MySQL 主从复制架构中，‌从库（Slave/Replica）‌ 特有的一种日志文件。它充当了主库与从库之间的“中转站”，用于暂存从主库接收到的二进制日志（Binlog）事件。

1. 核心作用
‌数据同步缓冲‌：主库将数据变更以 Binlog 形式发送给从库，从库的 I/O 线程将这些内容写入 Relay Log。随后，从库的 SQL 线程读取 Relay Log 并在本地重放这些操作，从而实现数据同步。
‌解耦读写压力‌：通过引入 Relay Log，主库发送日志和从库执行日志两个过程被分离开。I/O 线程负责接收，SQL 线程负责执行，两者互不阻塞，提高了复制的效率和稳定性。
‌断点续传与故障恢复‌：如果从库重启或网络中断，下次连接时可以从 Relay Log 中记录的位置继续执行，无需重新全量拉取数据。在从库发生故障时，也可通过解析 Relay Log 来恢复未应用的数据变更。
2. 关键特性
‌仅存在于从库‌：主库不会生成 Relay Log，只有在配置为主从复制角色的从服务器上才会产生。
‌格式与 Binlog 一致‌：Relay Log 的文件结构与主库的 Binlog 完全相同，这使得从库可以直接解析并执行其中的事件，无需格式转换。
‌自动清理‌：随着 SQL 线程不断执行 Relay Log 中的事件，旧的 Relay Log 文件会被自动删除或覆盖，以节省磁盘空间。
3. 工作流程简述
‌主库‌产生 Binlog。
‌从库 I/O 线程‌连接主库，拉取 Binlog 并写入本地的 ‌Relay Log‌。
‌从库 SQL 线程‌读取 ‌Relay Log‌，解析并执行其中的 SQL 语句，更新从库数据。
‌总结‌：Relay Log 是 MySQL 主从复制中确保数据最终一致性的关键组件，它通过异步缓冲机制，有效降低了主从同步对网络和磁盘 IO 的瞬时压力，并提供了可靠的断点续传能力。

### General Log（通用查询日志）

1. 核心作用
它会完整记录所有到达 MySQL 的 SQL 语句，包括：

客户端连接信息（IP、账号）
执行的完整 SQL 文本
操作的时间戳
甚至包含未成功执行的 SQL 语句

‌仅用于临时排查‌：只在需要追踪特定异常操作、审计可疑SQL时临时开启，排查完成后立即关闭

# 性能优化
### 慢 SQL
1. 发现
开启慢查询日志
MySQL 内置了慢查询日志功能，可以自动记录执行超时的 SQL。
‌配置参数‌：
slow_query_log = ON：开启日志。
long_query_time = 1：设定阈值（单位秒），超过 1 秒即记录。建议生产环境设为 0.5~1 秒。
slow_query_log_file：指定日志文件路径。

‌分析工具‌：使用 pt-query-digest 等工具对日志进行聚合分析，找出出现频率高、耗时长的“问题 SQL”。

实时监控
‌SHOW PROCESSLIST‌：实时查看当前正在运行的线程。重点关注 Time 列数值较大（如超过 10 秒）或 State 显示 Sending data、Creating tmp table、Sorting result 的进程。
‌性能监控平台‌：结合 Prometheus + Grafana 或云厂商的性能仪表盘，监控 QPS、RT（响应时间）和 CPU/IO 负载突增时刻对应的 SQL。

2. 分析
Explain 语句
| 字段 | 关注点 | 优化目标 |
| --- | --- | --- |
| ‌type‌ | 访问类型 | 避免 ALL（全表扫描），争取达到 ref、range 或 const 级别。 |
| ‌key‌ | 实际使用的索引 | 确认是否命中了预期索引。若为 NULL，说明未走索引。 |
| ‌rows‌ | 预估扫描行数 | 数值越小越好。若过大，说明索引区分度低或未生效。 |
| ‌Extra‌ | 额外信息 | ⚠️ 警惕 Using filesort（文件排序）和 Using temporary（临时表），这通常意味着需要建立联合索引或优化 SQL 结构。 |

3. 核心优化招数
索引优化（性价比最高）
补全缺失索引‌为 WHERE、ORDER BY、GROUP BY 涉及的列建立索引。
‌遵循最左前缀原则‌：联合索引 (a, b, c) 必须从 a 开始匹配，避免索引失效。
‌利用覆盖索引‌：将查询所需字段全部包含在索引中（如 SELECT id, name FROM users WHERE name='张三'，建立 (name, id) 索引），避免回表查询聚簇索引。

4. sql语句重构
‌拒绝 SELECT *‌：只查询业务需要的字段，减少网络传输和内存消耗。
‌优化深分页‌：对于 LIMIT 100000, 10，改用“延迟关联”或“游标法”
‌小表驱动大表‌：在 JOIN 查询中，确保驱动表（结果集小的表）在前，被驱动表建立索引。
‌替代子查询‌：尽量用 JOIN 替代复杂的嵌套子查询，特别是在 IN 或 EXISTS 场景中。

架构与配置调整
引入缓存‌：热点数据（如配置项、高频读取的用户信息）存入 Redis，减轻数据库压力。
‌分库分表‌：单表数据量超过千万级且读写压力大时，考虑垂直拆分（按列）或水平拆分（按行）。
**参数调优适当增大 innodb_buffer_pool_size（建议设为物理内存的 50%-70%，确保热点数据和索引能加载到内存中。

### 索引优化
索引优化‌的核心目标是：‌减少磁盘 IO 次数、避免回表、利用覆盖索引、确保索引高效命中‌。

一、SQL 写法优化（避免索引失效）
‌遵循最左前缀‌：联合索引 (a,b,c) 查询必须从 a 开始，避免跳过左侧列。
‌禁止对索引列做计算/函数‌：如 WHERE YEAR(create_time)=2023 改为范围查询 WHERE create_time BETWEEN '2023-01-01' AND '2023-12-31'。
‌字符串加引号‌：避免隐式类型转换导致索引失效。
‌模糊查询前置通配符‌：LIKE '%abc' 无法走索引，尽量用 LIKE 'abc%' 或全文索引。
‌避免 OR 连接无索引字段‌：确保 OR 两侧字段均有索引，否则退化为全表扫描。

二、索引设计优化（提升命中率）
‌区分度高的列建索引‌：如手机号、身份证；性别、状态等低区分度字段不建议单独建索引。
‌优先使用覆盖索引‌：将查询所需字段加入索引，避免回表。例如查询 SELECT id, name FROM users WHERE age=20，建立联合索引 (age, name, id)。
‌前缀索引优化长字符串‌：对于长文本字段（如邮箱、URL），只索引前 N 个字符，节省空间。

CREATE INDEX idx_email_prefix ON users(email(10)); // 取前 10 个字符当作索引 省空间 和 跑得快
‌控制索引数量‌单表索引建议不超过 5-7 个，过多会拖慢写入性能。

三、执行计划调优（EXPLAIN 实战）
‌消灭 type: ALL‌：确保查询至少走到 range 或 ref 级别。
‌消除 Using filesort‌：通过联合索引满足 ORDER BY 顺序，避免内存排序。
‌消除 Using temporary‌：优化 GROUP BY 和 DISTINCT，利用索引有序性。
‌关注 rows 估算值‌：若预估行数远大于实际返回，考虑更新统计信息 ANALYZE TABLE。

四、特殊场景优化
‌深分页优化‌：LIMIT 100000, 10 慢是因为要扫描前 10万行。
‌优化方案‌：利用覆盖索引先查主键，再关联原表。
SELECT * FROM orders o 
INNER JOIN (SELECT id FROM orders LIMIT 100000, 10) tmp ON o.id = tmp.id;
‌Count(*) 优化‌：InnoDB 会自动选择最小的二级索引进行计数，无需优化；MyISAM 直接读取元数据。
‌大字段分离‌：将 TEXT/BLOB 大字段拆分到扩展表，避免主表索引页过大。

### 分页优化
核心痛点在于‌深分页（Deep Pagination）‌导致的性能急剧下降。传统的 LIMIT offset, size 方式在偏移量很大时，数据库需要扫描并丢弃大量数据，效率极低。

1. 游标分页（Cursor-Based Pagination）—— 最优解
核心原理
不再使用 OFFSET 跳过数据，而是利用‌上一页最后一条记录的索引值‌作为游标，通过 WHERE 条件直接定位下一页的起始位置。

2. 延迟关联（Deferred Join）—— 兼容传统页码
如果业务必须支持“跳转到第 N 页”，无法使用游标分页，可采用此方案优化 OFFSET。

-- ❌ 传统写法：扫描 100000 + 20 行，然后丢弃前 100000 行
SELECT * FROM orders ORDER BY id DESC LIMIT 100000, 20;

-- ✅ 优化写法：子查询只查主键（走覆盖索引），再回表查详情
SELECT o.* // 开发中，推荐禁止使用*，通常要求必须把字段名一个个敲出来
FROM orders o
INNER JOIN (
    SELECT id FROM orders ORDER BY id DESC LIMIT 100000, 20
) AS tmp ON o.id = tmp.id;

减少 IO‌：子查询只需扫描索引树，无需读取整行数据，大幅减少磁盘 IO。
‌兼容性好‌：保留了传统页码跳转功能。

3. 限制最大页码与总数缓存
对于不需要精确总页数的大数据量场景，可通过业务手段规避深分页。

‌限制最大页数‌：例如只允许查看前 100 页，超过则提示“请细化搜索条件”。
‌估算总数‌：使用 EXPLAIN 中的 rows 或 Redis 缓存近似总数，避免执行耗时的 COUNT(*)。
‌禁止跳页‌：仅提供“上一页/下一页”按钮，引导用户使用游标分页逻辑。

4. 搜索引擎替代方案
当数据量达到千万级且查询条件复杂（多字段模糊搜索、多维度排序）时，MySQL 分页性能瓶颈难以通过 SQL 优化彻底解决。

‌引入 Elasticsearch / Solr‌：将数据同步至搜索引擎，利用其倒排索引和分布式能力处理复杂分页和搜索。
‌适用场景‌：电商商品搜索、日志检索、全文检索等。

| 场景 | 推荐方案 | 理由 |
| --- | --- | --- |
| ‌APP/网页无限滚动‌ | ‌游标分页‌ | 性能最好，无深分页问题，体验流畅 |
| ‌后台管理系统跳页‌ | ‌延迟关联‌ | 兼容页码跳转，比传统 OFFSET 快很多 |
| ‌超大数据量+复杂搜索‌ | ‌Elasticsearch‌ | MySQL 难以胜任复杂多维度的深分页 |
| ‌只需最新数据‌ | ‌限制最大页码‌ | 业务上规避深分页，最简单有效 |

### JOIN 优化‌
核心目标是减少磁盘 IO 和内存计算量。
根据 MySQL 的执行机制，优化 JOIN 主要围绕“索引”、“驱动表选择”和“数据过滤”三个维度展开。
1. 核心优化招数
 关联字段必须加索引（最重要）
 小表驱动大表
 先过滤再 JOIN

2. 高级特性：Hash Join (MySQL 8.0.18+)
对于‌等值连接‌且‌两表都很大‌的场景，MySQL 8.0.18+ 引入了 **Hash Join算法，比传统的 Nested Loop Join 快得多。

‌识别方法‌：使用 EXPLAIN FORMAT=TREE 查看执行计划，若出现 Hash join字样，说明已启用。
‌优势‌：无需依赖索引，直接在内存中构建哈希表进行匹配适合大规模数据的全表关联。

3. 如何验证优化生效？
使用 EXPLAIN 分析执行计划，重点关注以下指标：

‌type 列‌：

✅ ‌ref / eq_ref‌：表示使用了索引进行关联，性能良好。
❌ ‌ALL‌：表示全表扫描，必须优化。
⚠️ ‌index‌：全索引扫描，虽比全表好，但仍需优化。
‌Extra 列‌：

✅ ‌Using index‌：使用了覆盖索引，无需回表。
❌ ‌Using join buffer (Block Nested Loop)‌：表示使用了 Join Buffer 进行块嵌套循环，通常意味着被驱动表没走索引，性能较差。
❌ ‌Using filesort / Using temporary‌：出现了文件排序或临时表，需检查 ORDER BY 和 GROUP BY 字段是否命中索引。
‌rows 列‌：

数值越小越好。如果 rows 很大，说明统计信息可能过时，建议执行 ANALYZE TABLE table_name 更新统计信息。

‌小表驱动大表跑，先滤数据再连接；‌
‌Explain 看 type 列，拒绝 ALL 保性能。

### Buffer Pool
Buffer Pool‌ 是 InnoDB 引擎的核心内存缓存区域，它的核心作用是‌把磁盘上的表数据页、索引页提前缓存到内存，大幅减少磁盘IO，是MySQL高性能的基石‌。
关键配置与监控
sql
-- 查看当前Buffer Pool大小（单位字节）
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';

-- 查看缓存命中率，正常应在99%以上
SHOW STATUS LIKE 'Innodb_buffer_pool_read%';
如果命中率过低，说明Buffer Pool设置太小，大量请求直接访问磁盘，性能会严重下降。

### 连接池（Connection Pool）‌ 
是解决数据库频繁创建/销毁连接开销的核心组件，它通过‌复用已建立的物理连接‌，显著提升高并发场景下的系统性能。
1. 为什么需要连接池？
‌TCP 握手耗时‌：每次新建连接需经历三次握手、身份验证，耗时约几十毫秒。
‌资源消耗大‌：每个连接占用服务器内存和线程资源，频繁创建易导致 OOM 或连接数爆满。
‌连接池优势‌：预先创建一批连接放入池中，业务使用时直接“借”，用完“还”，避免重复建立连接的开销。

2. 核心工作流程
‌初始化‌：启动时创建 minIdle 个空闲连接。
‌获取连接‌：业务请求从池中借用空闲连接；若池满且未达 maxActive，则创建新连接；若已达上限，则排队等待或报错。
‌归还连接‌：业务执行完毕，将连接标记为空闲，放回池中供后续复用。
‌心跳检测‌：定期检测空闲连接有效性，剔除失效连接并补充新连接。

3. 主流连接池对比
| 连接池 | 特点 | 适用场景 |
| --- | --- | --- |
| ‌HikariCP‌ | 极速、轻量、零开销，Spring Boot 2.x+ 默认首选 | ‌绝大多数 Java 应用‌ |
| Druid | 阿里开源，功能强大，自带监控、SQL 防火墙 | 需要深度监控、防 SQL 注入的场景 |
| C3P0 | 老牌稳定，但性能较差，配置复杂 | 遗留系统维护 |

### 批量插入
批量插入‌是指将多条 INSERT 语句合并为一次网络请求发送给数据库执行。其核心目的是‌减少网络 IO 次数‌和‌降低事务提交开销‌，从而大幅提升写入性能。
1. 为什么快？
‌减少网络 RTT‌：1000 条单条插入需 1000 次网络往返；批量插入只需 1 次。
‌减少日志刷盘‌：InnoDB 的 Redo Log 和 Binlog 可以合并写入，减少磁盘 fsync 次数。
‌索引合并构建‌：B+Tree 索引可以一次性调整结构，避免每插一行都分裂页。
```
INSERT INTO users (name, age) VALUES 
('张三', 20),
('李四', 25),
('王五', 30);
```
2. 注意事项
| 注意点 | 说明 |
| --- | --- |
| ‌SQL 长度限制‌ | MySQL `max_allowed_packet默认约 4MB，单次批量过大需拆分 |
| ‌事务控制‌ | 批量插入建议包裹在事务中，失败可整体回滚，保证原子性 |
| ‌主键策略‌ | 建议使用雪花算法生成 ID，避免自增主键在分布式场景下的冲突或性能瓶颈 |
| ‌索引影响‌ | 若表上有大量二级索引，批量插入仍较慢，可考虑先删索引再重建 |

### Prepare Statement（预编译语句）
是数据库处理 SQL 的一种高效机制，它将 SQL 的‌结构解析‌与‌参数填充‌分离，核心优势在于‌防注入‌和‌高性能‌。

普通 SQL 执行是“每次都要重新解析”，而预编译语句分为两个阶段：
‌预处理（Prepare）‌：
客户端发送 SQL 模板（如 SELECT * FROM users WHERE id = ?）。
MySQL 进行‌语法解析、语义分析、生成执行计划‌。
MySQL 返回一个‌句柄（Statement ID）‌给客户端。
‌执行（Execute）‌：
客户端发送句柄 + 具体参数（如 id = 1001）。
MySQL 直接复用之前的执行计划，填入参数后执行。

为什么快？（性能优势）
| 对比项 | 普通 SQL (Statement) | 预编译 SQL (PreparedStatement) |
| --- | --- | --- |
| ‌解析开销‌ | 每次都要完整解析、优化、生成计划 | ‌仅第一次解析‌，后续直接复用计划 |
| ‌网络传输‌ | 每次发送完整 SQL 字符串 | 后续仅发送少量参数二进制数据 |
| ‌适用场景‌ | 一次性查询 | ‌高频重复执行同一结构 SQL‌（如批量插入循环） |

为什么安全？（防 SQL 注入）
‌普通 SQL拼接‌："SELECT * FROM users WHERE name = '" + userInput + "'"
若用户输入 ' OR '1'='1，SQL 结构被篡改，导致全表泄露。
‌预编译占位符‌：SELECT * FROM users WHERE name = ?
参数 ? 被视为‌纯数据值‌，而非 SQL 指令。即使输入 ' OR '1'='1，数据库也只会把它当作一个普通的字符串名字去查找，‌彻底杜绝注入‌。

# 主从复制
### Master & Slave
是主从复制（Master-Slave Replication）或高可用集群中的核心节点，主要负责处理‌写操作‌并生成二进制日志。
1. Master 的核心职责
‌处理写请求‌：所有 INSERT、UPDATE、DELETE 以及 DDL 操作必须在 Master 上执行。
‌生成 Binlog‌：将数据变更以二进制日志形式记录，用于主从同步和数据恢复。
‌维护事务一致性‌：作为唯一的数据写入源，保证数据的原子性和持久性。

2. 主从复制原理
Master 将数据变更写入 ‌Binlog‌。
Slave 的 I/O 线程连接 Master，拉取 Binlog 并写入本地的 ‌Relay Log‌
Slave 的 SQL 线程读取 Relay Log，重放操作以同步数据。

Relay Log 是只存在于 MySQL “从库（Slave/Replica）”上的临时中转日志，它是主从复制架构中，从库用来同步主库数据的“接力棒”。
作为主从复制架构中的“蓄水池”和“解力隔离带”，实现主库与从库之间的【异步解耦】。
核心作用：实现“异步复制”，解放主库的高并发能力；
缓冲垫作用：保护从库，防止从库被主库的“写入洪峰”冲垮
安全隔离作用：确保网络抖动或断电时，主从数据不丢失（容灾）

3.常见架构角色
 | 角色 | 职责 | 特点 |
| --- | --- | --- |
| ‌Master‌ | 写 + 读 | 单点写入，性能瓶颈所在，需高可用保护 |
| ‌Slave‌ | 只读 | 分担读压力，提供数据备份，存在同步延迟 |

4. 关键注意事项
‌单点故障风险‌：Master 宕机会导致整个集群不可写，通常配合 MHA、Orchestrator 或 MGR实现自动故障转移。
‌同步延迟‌：高并发写入时，Slave 可能滞后于 Master，导致“读写分离”场景下读取到旧数据。
‌半同步复制‌：为了解决数据丢失风险可开启半同步复制，确保至少一个 Slave 收到 Binlog 后才向客户端返回成功。

### GTID
GTID（Global Transaction Identifier，全局事务标识符）‌ 是 MySQL 5.6+ 引入的一种事务标识机制，用于在集群环境中唯一标识每一个已提交的事务。

1. 核心定义
GTID 是一个全局唯一的 ID，由 server_uuid:transaction_id 组成：

‌server_uuid‌：MySQL 实例的唯一标识（启动时生成）
‌transaction_id‌：该实例上按顺序递增的事务序号（从 1 开始）

2. 为什么需要 GTID？
在传统基于 Binlog 文件名和位置（File + Position）的主从复制中，切换主库或故障恢复非常复杂，容易出错。
| 特性 | 传统复制 (File+Pos) | GTID 复制 |
| --- | --- | --- |
| ‌主库切换‌ | 需人工计算新主库的 Binlog 位置，极易出错 | ‌自动定位‌，从库自动寻找缺失事务 |
| ‌幂等性‌ | 重复执行可能报错或数据不一致 | ‌自动跳过‌已执行的事务，保证安全 |
| ‌并行复制‌ | 依赖数据库名，限制较多 | 支持更细粒度的并行回放 |
| ‌运维复杂度‌ | 高，需手动记录 Position | ‌低‌，只需知道主库 IP 即可搭建从库 |

3. 命令
-- 查看当前已执行的 GTID 集合
SHOW GLOBAL VARIABLES LIKE 'gtid_executed';

-- 查看正在等待接收的 GTID
SHOW GLOBAL VARIABLES LIKE 'gtid_purged';

-- 搭建从库时指定主库（无需 File/Position）
CHANGE MASTER TO 
    MASTER_HOST='192.168.1.100',
    MASTER_USER='repl',
    MASTER_PASSWORD='password',
    MASTER_AUTO_POSITION = 1; -- 关键：启用自动位置定位

GTID 让 MySQL 主从复制从“手动挡”变成了“自动挡”，极大简化了高可用架构（如 MHA、Orchestrator）的故障切换流程。

### 半同步
主从复制的核心模式之一
1. 核心定义
主库提交事务时，不会立刻返回客户端成功，而是‌等待至少一个从库确认收到并写入日志后‌，才向客户端返回操作成功。

2. 与异步复制的核心区别
| 特性 | 异步复制 | 半同步复制 |
| --- | --- | --- |
| 主库提交行为 | 写完日志立刻返回，不等从库 | 等至少一个从库确认收到日志才返回 |
| 数据安全性 | 主库宕机可能丢失未同步的事务 | 已提交的事务至少在一个从库有备份，基本不丢数据 |
| 性能表现 | 无等待，吞吐量最高 | 增加几毫秒到几十毫秒延迟，轻微损耗写入性能 |

3. 适用场景
核心业务数据：订单、支付、账户余额等要求数据零丢失的场景
能接受轻微性能损耗，优先保证数据一致性的业务系统

4. 注意事项
如果所有从库都不可用，半同步会自动临时降级为异步复制，避免主库长时间阻塞，待从库恢复后自动切回半同步模式。

### 读写分离
是高并发场景下的经典架构优化方案，核心思路是：‌主库负责处理写请求（INSERT/UPDATE/DELETE），多个从库负责分担读请求，通过主从同步实现数据最终一致，大幅提升系统整体读吞吐量‌。

### 延迟复制
 是 MySQL 主从复制的一种特殊配置，让从库故意滞后主库一段时间再同步数据，是数据误操作场景下的核心兜底方案。
1. 核心作用
误操作兜底：主库误删表/误改数据后，可在从库延迟窗口内快速找回数据，避免全库恢复
规避逻辑错误：主库执行错误的批量更新时，从库不会立刻同步，给运维留出干预时间
读写分离缓冲：可用于规避主库瞬间高并发写入对从库的冲击

-- 设置从库延迟 3600 秒（1小时）后再同步主库数据
CHANGE MASTER TO MASTER_DELAY = 3600;
START SLAVE;

2. 注意事项
延迟是基于主库 binlog 的时间戳计算，不是从库本地时间
延迟期间从库仍会持续接收主库 binlog，只是暂不执行，不会丢失数据
紧急恢复时可临时执行 SET GLOBAL relay_log_info_repository='TABLE' 跳过延迟，立刻同步数据

# 高可用
下面的 MHA，Orchestrator，Keepalived，VIP，MySQL Router 是MySQL 高可用架构的核心组件，它们各司其职，共同实现数据库的故障自动切换、负载均衡和服务连续性。
| 组件 | 核心作用 | 定位 |
| --- | --- | --- |
| ‌MHA‌ | 经典 MySQL 主从自动故障切换工具 | 传统高可用方案，轻量无侵入 |
| ‌Orchestrator‌ | 开源 MySQL 复制拓扑管理与故障自愈平台 | 新一代可视化高可用，支持复杂拓扑 |
| ‌Keepalived‌ | 基于 VRRP 协议实现虚拟 IP 漂移 | 网络层高可用，保证入口连续性 |
| ‌VIP‌ | 虚拟 IP 地址，不绑定固定物理机 | 对外统一访问入口，屏蔽后端节点变化 |
| ‌MySQL Router‌ | MySQL 官方轻量中间件 | 读写分离、负载均衡、路由转发 |

### MHA
‌核心能力‌：监控主库状态，主库宕机后自动选出新主库，修复其余从库指向新主库，完成故障切换。
‌优势‌：轻量、不侵入 MySQL 代码，无需修改现有主从架构。
‌局限‌：社区维护活跃度降低，切换速度依赖 SSH 连通性，对大集群拓扑支持有限。

### Orchestrator
核心能力‌：Web 可视化界面管理 MySQL 复制拓扑，支持自动故障检测、选主、切换，支持 GTID、半同步、链式复制等复杂场景。
‌优势‌：功能强大，支持手动干预拓扑调整，故障自愈能力强，是当前主流开源方案。
‌典型场景‌：中大型 MySQL 集群，需要可视化运维和自动化故障处理的环境。

### Keepalived + VIP
‌工作原理‌：Keepalived 通过 VRRP 协议在多台机器之间争抢同一个虚拟 IP（VIP），主节点宕机后，VIP 自动漂移到备节点。
‌作用‌：对外提供一个永不变化的数据库连接地址，应用层完全感知不到后端主库的物理 IP 变化，无需修改连接配置。
‌注意‌：VIP 必须和数据库节点在同一局域网段内。

### MySQL Router
‌核心能力‌：官方提供的轻量数据库中间件，自动将读写请求路由到不同节点，实现读写分离，还能自动感知元数据变化，配合 InnoDB Cluster 使用。
‌优势‌：和 MySQL 兼容性最好，无额外学习成本，支持连接池管理。
‌定位‌：介于应用和数据库之间的轻量代理，分担读写流量，提升集群整体吞吐量。

### 经典架构
生产环境最常用的高可用组合是：
‌Orchestrator/MHA（故障切换） + Keepalived + VIP（入口漂移） + MySQL Router（读写分离）

# MySQL8 新特性
### CTE
CTE（Common Table Expression，公用表表达式）‌ 是 SQL:1999 标准引入的特性，在 MySQL 8.0+ 中正式支持。它允许你为复杂的子查询定义一个‌临时命名结果集‌，使 SQL 语句更具可读性和可维护性。
1. 核心语法
使用 WITH 关键字定义
WITH cte_name (column1, column2) AS (
    SELECT ... -- 定义临时结果集
)
SELECT * FROM cte_name; -- 引用临时结果集

2. 与传统子查询的区别
| 特性 | 传统子查询 | CTE |
| --- | --- | --- |
| ‌可读性‌ | 嵌套多层，逻辑混乱 | 线性结构，逻辑清晰 |
| ‌复用性‌ | 相同逻辑需重复写多次 | 定义一次，可多次引用 |
| ‌递归支持‌ | 不支持 | 支持‌递归查询‌（处理树形结构必备） |

3. 典型应用场景
非递归：
-- 查询每个部门的平均薪资，并找出高于公司平均薪资的部门
WITH DeptAvg AS (
    SELECT department_id, AVG(salary) as avg_sal
    FROM employees
    GROUP BY department_id
),
CompanyAvg AS (
    SELECT AVG(salary) as comp_avg FROM employees
)
SELECT d.department_id, d.avg_sal
FROM DeptAvg d, CompanyAvg c
WHERE d.avg_sal > c.comp_avg;

递归：
-- 查询 ID 为 1 的员工及其所有下属（递归）
WITH RECURSIVE Subordinates AS ( // 定义一个下属的临时结果集 RECURSIVE 递归关键字
    -- 锚点成员：初始查询
    SELECT id, name, manager_id, 1 as level // 1 as level 定义一个虚拟列 1是第一层
    FROM employees
    WHERE id = 1
    
    UNION ALL // 将“起点老大”和下面“源源不断抓出来的下属们”横向拼在一张表里。
    
    -- 递归成员：连接自身
    SELECT e.id, e.name, e.manager_id, s.level + 1 // 每往下抓一代，层级数自动累加 1。
    FROM employees e
    INNER JOIN Subordinates s ON e.manager_id = s.id // 连接自身
)
SELECT * FROM Subordinates;

### 窗口函数
ROW_NUMBER()：强制唯一序号
RANK():跳跃式排名
DENSE_RANK():密集连续排名

| 函数 | 中文名 | 处理并列值 | 排名是否连续 | 示例结果 (10k, 8k, 8k, 7k) |
| --- | --- | --- | --- | --- |
| ‌ROW_NUMBER()‌ | 行号 | ‌不并列‌，强制唯一序号 | ✅ 连续 (1,2,3,4) | 1, 2, 3, 4 |
| ‌RANK()‌ | 跳跃排名 | ‌并列‌，相同值排名相同 | ❌ 不连续 (跳号) | 1, 2, 2, 4 |
| ‌DENSE_RANK()‌ | 密集排名 | ‌并列‌，相同值排名相同 | ✅ 连续 (不跳号) | 1, 2, 2, 3 |

总结选择指南
想要‌每行唯一 ID‌ 或 ‌去重‌ ➡️ 选 ROW_NUMBER()
想要‌真实名次‌且‌允许空缺‌（如比赛排名） ➡️ 选 RANK()
想要‌连续档位‌且‌不允许空缺‌（如等级评定） ➡️ 选 DENSE_RANK()

### 递归查询
在 MySQL 中实现‌递归查询‌（通常用于处理树形结构数据，如部门层级、菜单目录、评论回复链）主要有两种方式：‌CTE 递归（推荐，MySQL 8.0+）‌ 和 ‌自定义变量/存储过程（旧版本兼容方案）‌。

| 方案 | 描述 | 缺点 |
| --- | --- | --- |
| ‌应用层递归‌ | 代码中多次查询数据库组装树 | IO 次数多，N+1 问题严重 |
| ‌路径枚举字段‌表中增加 ancestors 字段（如 ,1,5,10,） | 用 LIKE '%,10,%' 查询 | 维护成本高，插入/移动节点需更新大量数据 |
| ‌嵌套集模型‌ | 增加 lft, rgt 字段表示区间 | 插入/删除节点时需重新计算整个树的区间，写入极慢 |

### Invisible Index
Invisible Index（不可见索引）‌ 是 MySQL 8.0 引入的特性，它不会被查询优化器使用，但索引本身仍然正常维护和更新。
1. 核心作用
这是一个非常安全的索引“下线”工具：

索引对优化器不可见，查询不会走它，但不会立刻删除索引
可以在不影响线上业务的前提下，观察删除该索引后系统的性能变化
避免直接 DROP INDEX 后引发慢查询，方便快速回滚
2. 基本用法
-- 创建不可见索引
CREATE INDEX idx_phone ON users(phone) INVISIBLE;

-- 将已有索引改为不可见
ALTER TABLE users ALTER INDEX idx_name INVISIBLE;

-- 恢复为可见索引
ALTER TABLE users ALTER INDEX idx_name VISIBLE;
3. 关键特性
主键索引不能设为不可见，否则会报错
即使索引不可见，DML 操作（INSERT/UPDATE/DELETE）仍然会正常维护它，不会降低写入性能
可以通过 SHOW INDEX FROM table_name 查看索引的 Visible 状态
4. 典型使用场景
‌索引清理‌：怀疑某个索引是冗余的，先设为不可见，观察几天无异常再正式删除
‌灰度测试‌：想测试删除索引后的性能影响，又怕出问题，用不可见索引做“软删除”
‌紧急回滚‌：如果误删了重要索引，之前设为不可见的索引可以立刻恢复可见，秒级恢复性能

### Generated Column
Generated Column（生成列）‌ 是 MySQL 5.7+ 引入的特性，指字段的值不是直接插入，而是由其他列通过表达式‌自动计算生成‌。
| 类型 | 关键字 | 存储方式 | 特点 |
| --- | --- | --- | --- |
| ‌虚拟生成列‌ | VIRTUAL (默认) | ‌不存磁盘‌，查询时实时计算 | 不占空间，但每次读取都要算，不能建索引（5.7不支持，8.0支持部分） |
| ‌存储生成列‌ | STORED | ‌存入磁盘‌，更新时计算并保存 | 占空间，但读取快，‌可以建索引‌，常用于优化查询 |

CREATE TABLE orders (
    id INT PRIMARY KEY,
    price DECIMAL(10, 2),
    quantity INT,
    
    -- ✅ 虚拟生成列：不占空间
    total_virtual DECIMAL(12, 2) GENERATED ALWAYS AS (price * quantity) VIRTUAL,
    
    -- ✅ 存储生成列：占空间，可建索引
    total_stored DECIMAL(12, 2) GENERATED ALWAYS AS (price * quantity) STORED
);

-- 为存储列建索引，加速范围查询
CREATE INDEX idx_total ON orders(total_stored);

### JSON
JSON‌ 是 MySQL 5.7+ 正式引入的原生数据类型，专门用于存储半结构化的非结构化数据，无需提前定义固定字段，是处理灵活属性场景的最佳选择。

### 函数索引
函数索引（Functional Index）‌ 是 MySQL 8.0.13+ 引入的特性，允许在索引中使用表达式或函数，专门解决“对索引列做计算导致索引失效”的痛点。
函数索引通过‌预先计算并存储函数结果‌，让查询可以直接命中索引。
